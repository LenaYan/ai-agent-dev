# 流水线的可复现性：同一份输入跑三次，图对不上

> 2026-07-28。起因：修完边审核的输入 bug 后重跑流水线，24 个评测标签里
> 12 个的节点 id 失效。追下去发现的问题比标签失效大得多。

## 一句话

**同一份课标原文、同一套代码、四层全都 `temperature=0`，跑三次得到三张对不上的图**
——两两之间节点名 Jaccard 只有 29%~52%。而**这个动荡里约七成不是内容变了，是名字被改写了**，
配上"id = 名称的哈希"这个设计，就变成了节点身份的全面洗牌。

## 怎么量的

三次独立抽取：A（2026-07-27 那轮）、B（2026-07-28 修完边审核后重跑）、
C（当天只跑抽取层的第三次）。都用 `deepseek-v4-flash`、`temperature=0`、同一份
`01-chunks.json`（切分是纯规则的，三次完全相同）。

| 配对 | 节点名 Jaccard | 同名节点 | 误概念字面相关度中位数 | 低于生产门槛 0.2 |
|---|---|---|---|---|
| A-B | 52% | 48 | 0.433 | 25% |
| A-C | 32% | 36 | 0.380 | 22% |
| B-C | 29% | 32 | 0.500 | 16% |

## 两个失败模式，性质完全不同

### ① 整块 chunk 颗粒无收，而且每次是不同的几块

28 个 chunk 里 **8 个（29%）至少有一次产不出任何 draft**：

```
#001 缺席 B ｜ #004 缺席 A/B ｜ #005 缺席 B ｜ #006 缺席 A
#010 缺席 A/B ｜ #016 缺席 A/B ｜ #019 缺席 C ｜ #025 缺席 C
```

这是最大的一块损失——整组知识点连同它们的误概念一起消失。落在
`dropped.json` 里是 `NO_DRAFTS`，**留痕了，但没人看**。

### ② 命名的同义改写（占身份动荡的大头）

三次都有产出的 20 个 chunk 里，只有 10 个的名称集合完全一致。但差异的形状是这样的：

```
比较万以内数的大小   vs  万以内数的大小比较        ← 词序
探索并掌握多位数乘法  vs  探索并掌握多位数的乘法     ← 一个"的"
了解十进制计数法     vs  十进制计数法              ← 去掉动词
初步的应用意识       vs  初步形成应用意识
用计算器探索简单规律  vs  借助计算器探索简单规律
计数单位的感悟       vs  计数单位
```

量化：A 有而 B 没有的 22 个名称里，**14 个（64%）能在 B 里找到字面相似度 ≥0.6
的对应项**；B→C 这个比例是 **80%**（32/40）。相似度 1.00 的那些是完全包含关系
（"计数单位的感悟" ⊃ "计数单位"）。

**也就是说：内容大体是稳的，抖的是措辞。**

## 根因：用名称的哈希做节点身份，把措辞抖动放大成身份变更

```python
def make_topic_id(content: DraftContent) -> str:
    """确定性 id：重排输入不改变结果，便于比对两次跑的差异。

    取 (name, domain, grade_start) 而非序号，是为了让 id 在增删条目时保持稳定。
    """
    seed = f"{content.name}|{content.domain}|{content.grade_start}"
    return "t_" + hashlib.sha1(seed.encode("utf-8")).hexdigest()[:10]
```

这个设计**防的是"增删条目导致序号平移"**——docstring 写得很清楚。问题在于：
实测下来占主导的动荡**不是增删，是改写**，而名称哈希对改写零抵抗力。

**为一种威胁做了防护，而现实中占主导的是另一种。** 这不是写这段代码时能预见的
——它需要"同一输入跑三次再比对"这个动作，而那个动作直到今天才第一次做。

## 单次调用其实相当稳，不稳的是跨运行

同一个 chunk 连发三次（`temperature=0`）：3 个 chunk 里 2 个的**名称集合三次完全一致**，
只有误概念文本在变；第三个（#006）名称不一致，差异是切分粒度
（"体会数和运算的意义" 1 个 vs 拆成"在生活情境中体会数的意义"+"…运算的意义" 2 个）。

所以"模型完全随机"这个说法是不对的。更准确的说法是：**措辞与切分粒度处在一个
浅的势阱里，同一次会话内倾向一致，跨会话/跨天会漂**。（`temperature=0` 对
MoE 架构不保证确定性——路由与批处理都会引入非确定性——但这里的漂移幅度
远大于纯采样噪声能解释的范围。）

## 这件事的射程

**没有被推翻的**：字面 vs 向量那轮受控对比仍然有效。那轮**把图固定住、只换打分器**，
是干净的单变量对比，79% vs 53% 不受影响。

**被推翻的**：任何**跨重跑**的 recall 比较。"新图比旧图掉 17 个百分点"这句话里，
有多少是边审核修复的副作用、有多少是抽签，说不清。

**新暴露的**：这个项目的立项理由是"真正的资产是流水线，不是数据集"
（见 `feasibility-analysis.md`）。而一条依赖图如果每次生成都换掉一半节点身份，
**下游没法在它上面建任何东西** —— 评测标签活不过一次重跑只是最先撞上的那个症状。
这直接冲击"流水线可复用"这个前提，需要正面回答。

1. ~~**查 `NO_DRAFTS`：29% 的 chunk 至少一次颗粒无收。**~~
   **[2026-07-28 已查并已修，见下节]**

2. **节点身份不要挂在名称上。** 切分是纯规则、完全确定的，`standard_code`
   与 chunk 序号是稳的。可选方向：id 锚在 `standard_code` + chunk 内序号；
   或者维护一张稳定 id 注册表，新一轮的节点按相似度认领已有 id（阈值可用
   本文量出来的 0.6）。两者都要处理"一个 chunk 这次出 3 个、下次出 2 个"的对齐。

3. **评测标签解耦运行**：不再挂节点 id，改挂"课标条目编号 + 误概念的语义描述"。
   但注意这治的是症状——**给一张每次都变的图做稳定标签，是在给流沙打地基**。
   1 和 2 没解决之前，3 的收益有限。

## 一条方法论

这次的教训和本仓库反复撞的那条是同一个：**先确认度量在量你以为它在量的东西。**

前几次是"长度惩罚冒充模型问题"（recall 63%）、"空样本分母只有 3"、
"边审核缺输入冒充模型能力差"。这次是**"抽签结果冒充质量变化"**：
两张图的 recall 差 17 个百分点，看起来像是某个改动的效果，实际上重跑一次就能
摆动同样的幅度。

可推广的规则：**任何跨运行的数字对比，先证明这条流水线是可复现的。**
在此之前，所有"改了 X 之后指标变化 Y"的结论都欠一个前提。

## 追查 ①（`NO_DRAFTS`）的结果：逃生舱被误用，重试即可，与模型强弱无关

**排除的假设**（都是先量再排，不是猜）：

- **不是长度**：不稳的 chunk 中位 42 字，稳的 40 字，范围完全重叠。
- **不是调用失败**：extract 阶段的丢弃里 9 条 `NO_DRAFTS`、只有 1 条
  `EXTRACT_FAILED` —— 模型**确实返回了空列表**，不是 API 出错。
- **不是模型不够强**：同一 chunk 连发 5 次，`deepseek-v4-flash` 与
  `deepseek-v4-pro` 的空返回率没有差别（pro 在 #004 上还更高，2/5 vs 1/5）。
  **换模型解决不了。**

**根因**：`_SYSTEM` 里那句"如果拆不出任何可教的知识点，返回空列表"是个逃生舱，
而它被误用在明显可教的内容上 —— #004 的原文是"探索加法和减法的算理与算法，
会整数加减法"。每次调用约 20~40% 概率走这个逃生舱。

**修法**：空返回重试（`EMPTY_RETRIES = 2`，即最多试 3 次）。

**为什么这不是"逼模型硬凑"**：素材里 28 条逐条读过，全部是实打实的课标条目，
没有一条拆不出可教的知识点。所以空返回一律是误判。仍设上限、且全空时照常记
`NO_DRAFTS`，并在 detail 里写明试了几次 —— 将来素材里真有空条目（比如章节标题
被误切成 chunk）时它还是会被如实记下来。

### 一个被证伪的怀疑，记下来免得重来

加完重试的第一轮里 #004 连空 3 次，当时怀疑**重试发的是逐字相同的请求、
撞上了服务端缓存**（若成立，加重试次数无效，得给请求带扰动）。

**实测证伪**：对 #004 跑 8 轮重试 ——

| | 基础空返回率 | `P(空 given 上一次空)` |
|---|---|---|
| 原样重试（请求逐字相同） | 2/10 = 20% | **0/2 = 0%** |
| 带扰动重试（附尝试序号） | 1/9 = 11% | 0/1 = 0% |

若真被缓存粘住，这两个条件概率应该接近 100%。（条件样本只有 2 与 1 个，
证据强度有限，但方向明确反对粘滞。）

而"连空 3 次"根本不需要额外解释：基础率 20% 下单 chunk 连空三次是 0.8%，
**28 个 chunk 里至少出现一个的概率是 1-0.992^28 ≈ 20%** —— 一轮里撞上一个是正常的。
这也是上限定在 2 就够的理由：期望每轮残留不到 1 个 chunk。

### 没有宣称的东西

带重试跑一轮，覆盖 26/28。**这不构成"改进幅度"的证据** —— 此前三次运行的覆盖
分别是 24/23/26，这次落在同一范围内，而本文前半段刚证明单次运行的方差足以吞掉
这种差异。**不能在自己的改动上放宽刚给别人定的标准。** 能说的只有：机制对
（三次全空的期望概率降到个位数百分比）、记账变清楚了（"重试过仍空"与"一次就空"
现在可区分）。要证明幅度，需要带重试连跑三次再比 Jaccard。

### 剩下的那一半没动

②（命名同义改写被 `make_topic_id = sha1(name|…)` 放大成身份变更）**原样未修**。
它才是评测标签死掉的直接原因，也是"图不可复现"的另一半。方向见上文第 2 条。

## 验收（2026-07-29）：两处修复各自贡献可分离，身份稳定性 42% → 70%

带上全部修复（空返回重试 + 稳定 id 注册表）重跑三次抽取，与修复前的三次对照。
**判据是跑之前就写死的**（覆盖率该明显上去；Jaccard 该涨但不该涨到 80%+，
否则说明"29% 整块缺失 + 七成同义改写"这个成分拆分判断错了）。

| 指标 | 修复前 | 修复后 |
|---|---|---|
| chunk 覆盖（共 28） | 24 / 23 / 26 | **26 / 27 / 28** |
| 节点名 Jaccard（中位） | **32%** | **57%** |
| id Jaccard（中位） | — | **70%** |

**两处修复的贡献可以分离。** 拿修复后这同样三次产出，只换 id 方案做对照：

| id 方案 | r1-r2 | r1-r3 | r2-r3 | 中位 |
|---|---|---|---|---|
| 旧 `sha1(name)` | 48% | 42% | 39% | 42% |
| 注册表 | **76%** | **70%** | **69%** | **70%** |

也就是说：**重试把节点名 Jaccard 从 32% 抬到 57%**（补回整块缺失的 chunk），
**注册表在此基础上把 id 稳定性再抬 28 个百分点**（吸收同义改写）。
实测 57% 落在事先划定的区间内，成分拆分的判断站得住。

### 一个混淆因素，查过了

r1/r2/r3 跑得比较集中，而 A/B/C 跨了两天。本文前面记过"措辞同会话内倾向一致、
跨会话会漂"—— 那这个改进会不会只是**时间接近**造成的？

**不是。** B 与 C 是同一天跑的，Jaccard 只有 **29%**；而 r1 与 r2 跨天，
Jaccard 是 **67%**。时间接近解释不了这个差距。

### 仍然没有解决的

- **三成的 id 活不过重跑。** 从"每次重挂一半标签"降到"重挂三成"，不是消灭。
- **命名措辞的抖动一点没修**（节点名 Jaccard 只有 57%），也不该由这两处修复来修 ——
  注册表只是让它不再传导到身份上。真要修得动切分粒度与命名约束。
- **`#004` 是顽固户**：三次里两次仍然空返回（原文"探索加法和减法的算理与算法，
  会整数加减法"）。重试上限提到 3 次能不能救它，没测。
- **n=3。** 三次运行的中位数不是稳定估计。

## 带全部修复的第一次全量重跑（2026-07-29）

上一节的验收只跑了抽取层（约 110 次调用）。这一次是**完整六层真跑**
（`--engine langgraph-fanout`，约 1000 次调用、11 分钟），产出即当前的
`data/generated/`，并**第一次写出 `data/topic-registry.json`**。

### 开跑前修掉的一个缺口：注册表只接在手写引擎上

`run.run_pipeline` 里有 `TopicRegistry.load / assemble(registry=) / save`，
而 `graph.node_assemble`（**两个 LangGraph 引擎共用同一个函数**）调 `assemble`
时没传 registry，静默退回 `sha1(name)`。

这个缺口能躲过既有的逐字节跨引擎对等比对（`test_two_engines_produce_
identical_artifacts_on_normal_run`），原因值得记：**空注册表首轮认领不到任何
条目，两条路径给出的 id 恰好相同**。差异要到第二轮才现形 —— 注册表根本没落盘，
同义改写照样换身份。所以补的测试是**跑两轮**、中间把节点名做同义改写，断言 id
不变（`test_synonymous_rename_keeps_topic_ids_across_reruns`，三个引擎各一份）。
RED 时手写版通过、两个 LangGraph 引擎全挂，形状正确。

### 图的形状：每一项都变好，代价也如实记着

| 指标 | 基线 07-28 | 本轮 07-29 |
|---|---|---|
| 有产出的 chunk | 23 / 28 | **28 / 28** |
| draft 条数 | 75 | 93 |
| 候选边 | 331 | 453 |
| 最终节点 | 66 | **78** |
| 最终依赖边 | 162 | **213** |
| 孤立节点 | 7（11%） | **4（5%）** |
| 最长前置链 | 10 | **12** |
| `NO_DRAFTS` / `EXTRACT_FAILED` | 4 / 1 | **0 / 0** |
| `REVIEW_REJECTED` | 126 | 175 |
| `EDGE_TARGET_REJECTED` | 38 | 58 |

校验结果 **0 error / 4 warning**（4 个 `ISOLATED_TOPIC`：公倍数、公因数、
质数与合数、几何直观）。淘汰数同比例上涨 —— 素材多了，被否的也多，不是白捡。

**这仍然只是一次运行。** 按本文前半段自己立的规矩，单次覆盖数（28/28）不能
当改进幅度用（修复前三次是 24/23/26）。能说的是机制在起作用。

### 注册表这轮拿不到红利，而且不能靠"种子化"提前拿

注册表是本轮**第一次创建**（空表起步），认领不到任何旧身份，所以 78 个节点全是
新条目，评测标签该死的照样死（17 条计召回样本里 8 条锚点全失效）。红利要从
下一轮开始兑现。

试过一个想法并**否掉了**：用基线图的 66 个节点**种子化**注册表，让本轮去认领，
标签就能大批存活。离线干跑（零调用）的结果是 45 个认领、标签存活从 9/17 涨到
14/17 —— 但逐条看认领明细，多出来的里面有假合并：

| 认领对 | 名称相似 | 描述相似 | 合成 | 判断 |
|---|---|---|---|---|
| 小数的意义 → 万以内数的意义 | 0.750 | **0.265** | **0.604** | **假合并**，高出门槛 0.004 |
| 比例的含义 → 按比例分配的含义 | 0.750 | 0.522 | 0.682 | 两个知识点 |
| 比较万以内数的大小 → 万以内数的大小比较 | 0.875 | 0.280 | 0.696 | 同一个，真 |
| 计数单位 → 计数单位的感悟 | 1.000 | 0.481 | 0.844 | 同一个，真 |

「小数的意义」正是三条小数样本的锚点 —— 种子化会把它们挂到一个**讲整数**的
节点上，指标变好、标签变错。**「只看存活率会选出错误的方案」这条教训，换个
场景又发生了一次。**

同时这给了 `CLAIM_THRESHOLD = 0.6` 一个新的读数：它是在**三次同管道运行**上
校准的、当时实测 0 假合并；第一次让它跨越更大的名称集变动（66 → 78 节点），
45 个认领里就出现 2 个假合并（4%）。更麻烦的是**没有余量** —— 假合并 0.604
排在真认领 0.696 / 0.844 下面却仍然过线，而把门槛提到 0.62 只能挡掉这一个，
挡不住 0.682 那个。描述相似度 0.265 本来是个诚实的反对票，被 0.7 的名称权重
压过去了。**要真修，方向是权重/门槛之外的判据，不是把旋钮再拧一格。**

### 评测：三张图串起来看，不是"掉了 14 个点"

标签逐条重挂后（依据一律是"新图哪个节点的误概念原文对得上"，不按检索排序挑），
在同一工作点（阈值 0.25、空样本正确率 100%）：

| 图 | recall@3 | 说明 |
|---|---|---|
| 07-27（64 节点） | 79% | `rag-vs-literal.md` 里记的那个数 |
| 07-28（66 节点） | **59%** | 本轮实测复现，对应 learning-log 里"掉了 17 个百分点" |
| 07-29（78 节点） | **65%** | 本轮 |

**跨图直接比 recall 是不成立的** —— 分母、样本、标签本身都在变。要比就限定到
两轮都存在的同一批 15 条观察句，各挂各图的锚点：

| | recall@1 | recall@3 |
|---|---|---|
| 基线图 07-28 | 53% | **53%** |
| 新图 07-29 | 60% | **67%** |

逐条配对：**两边都中 7｜新图独赢 3｜基线独赢 1｜都不中 4**。
**4 对不一致的符号检验双侧 p ≈ 0.63 —— 这 14pp 与噪声区分不开，不能宣称
"检索变好了"。** 而且新图独赢的三条（`dec_more_digits_bigger`、
`dec_compare_digits`、`zero_not_even`）赢的原因**不是检索变强**，是新图里
终于有了对得上的节点（数感的进一步发展、奇数与偶数都回来了），标签能挂对地方。

### 两个覆盖缺口，单独记账不混进 recall

有两条样本在新图里**没有任何节点带那条误概念**：

- `dec_trailing_zero`（0.50 比 0.5 大）—— 所有小数节点都不讲末尾零；
- `subtraction_commutes`（减法也能交换）—— 「加法交换律」节点还在，
  但这轮只剩「交换位置后和会变」，丢了「对减法也成立」那条。

留着它们等于让检索指标永久背一个没人能答对的锅；直接删掉又**正好删掉新图最差
的两条**，把数字修饰得好看。取的折中是：移出计召回集（同 07-28 的先例），
但**覆盖缺口单独报**，见 `rag-vs-literal-backlog.md`。

反过来，07-28 因同样理由删掉的两条**按当时写下的条件加了回来** ——
`简单的分数四则运算` 与 `比的含义` 都回到图里且误概念对得上。其中
`比的含义` 的 id `t_40f1cd2652` **与删除前完全相同**（名称/领域/起始学段没变，
sha1 自然一致）。加回来之后 recall@3 从 67% 变成 65%（`ratio_is_quotient`
没命中）—— **会拉低分数不是不加的理由，条件满足就加。**

## 内容漂移：把「节点在 ≠ 误概念在」变成一个可以量的数（2026-08-05）

上一节末尾那两个覆盖缺口里，`subtraction_commutes` 的形状值得单独拎出来：

> 「加法交换律」节点还在（id 认领成功、身份指标全绿），
> 但它这轮只剩「交换位置后和会变」，**丢了「对减法也成立」那条误概念**。

注册表稳的是身份，**内容有没有跟着留下来，此前一个数都没有**。而误概念是
这张图对诊断类应用的全部价值 —— 身份留存率报 70%、误概念悄悄掉一半，
下游看到"图很稳"，拿到的是空壳。

### 工具：`scripts/compare_runs.py`

    uv run python scripts/compare_runs.py 上一轮/graph.json 这一轮/graph.json

**两层指标，分母不同，刻意不混：**

| 层 | 指标 | 分母 |
|---|---|---|
| 身份 | id Jaccard、名称 Jaccard、**id 留住但改名的条数** | 两轮的全部节点 |
| 内容 | 原文未改留存、含改写留存、空壳节点数、丢失明细 | **只有 id 两轮都在的节点** |

身份没留住的节点不进内容层分母 —— 节点都换身份了，说它误概念丢了没有意义，
那是身份问题、上一层已经记过一次账。同 `eval_diagnosis.py` 里"空样本不进召回
分母"的纪律。

**三个防虚高的设计**（这个度量最大的风险是它自己造出一个好看但错误的数）：

1. **精确留存与含改写留存分开报，两者之差就是改写的量。** 名称那层已经吃过
   一次亏（看起来的动荡七成是措辞变了），误概念是整句自然语言，更容易被重写；
   只报精确留存必然把改写算成丢失，得出虚高的抖动。
2. **配对是贪心一对一。** 没有这条，一条被拆成两条的误概念会双双认领同一个
   前身，留存率被重复计数顶高。同 `topic_registry` 的约束和理由。
3. **"原文没变"走字符串相等，不看分数。** `LiteralScorer` 是双向覆盖率取
   大者，对包含关系给满分（实测 "计数单位的感悟" ⊃ "计数单位" = 1.00），
   拿满分当"原文相同"会把一次真实的截短算成没变。

### 这个工具的数字现在还不能引用

`DEFAULT_MATCH_THRESHOLD = 0.6` **没有任何实测标定** —— 它不像
`CLAIM_THRESHOLD` 那样是在三次真实运行上量出来的，只是与后者取同一量级
方便对读。误概念是长句，bigram 基数比名称大得多、通用措辞更多，很可能该
定得更高。

所以脚本默认打印**一整条阈值敏感性曲线**而不是一个单点：曲线平说明配对
干脆（改写幅度小），单点可信；一路滑坡说明大量配对卡在门槛附近，那个单点
就是抽签。**在真图上读过这条曲线之前，任何单点留存率都只是那个阈值下的读数。**

同理，这个脚本**不设闸门、永远返回 0**。漂移多少算"太多"目前没有依据，
拍一个数当阈值只会造出第四个"看起来有根据"的假指标。它是量具，不是判据。

### 它同时回答了注册表那个悬着的问题

2026-07-29 那轮是**空注册表起步**，认领不到任何旧身份，所以那轮的 id 稳定性
无从谈起 —— 注册表的红利要到下一轮才开始兑现。下一轮该看的两个数，正好都在
这个脚本的身份层里：**id Jaccard 是不是接近验收时离线复算的 70%**，以及
**「id 留住但改名」有多少条** —— 后者才是注册表真正做功的证据（名字变了、
身份没变，正是它被造出来要干的事）。

一次重跑同时喂两个问题，是刻意的：跑一轮是 ~1000 次调用 / 11 分钟，
拆成两个脚本会诱使人只跑一个。
