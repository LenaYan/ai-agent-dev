# 设计：字面匹配 vs 向量检索的受控对比

> 时间：2026-07-27。状态：设计已定，实现未开始。
> 前置：`docs/mcp-server-design.md`（§1 决定领域层不放 LLM、§7 实测结果）、`memory/decisions.md` ADR-0006。
> 路线图对应：阶段三·上下文与记忆系统（RAG），本工作区此前完全空白。

## 0. 为什么现在做这件事，以及为什么是这个形式

上一轮把诊断检索从 63% 修到 84% 的过程中，**顺手造出了一台受控实验台**：

- 22 条 ground truth（含同义换词、跨年级同主题、3 条"应当召回不到"）
- 一个跑得通、零 key、零成本的 `recall@3` 评测脚本
- 一个纯函数领域层 —— 换检索实现，工具面与 55 条测试一行不动
- 一个**字面匹配的基线数字 84%**，以及它的失败模式清单

而剩下的 3 条未命中都指向同一件事：**具体数字被换掉后字面匹配就废了**
（`20+5×2` vs 图里 `15+3×4`）。这正是向量检索天然要解决的问题。

**阶段三的入口是这个项目自己用数据指出来的，不是路线图规定的。** 这与
"读到一句警告就写待办"有本质区别（见 memory 2026-07-27 那条元收获）。

### 这个实验要回答的问题

一句话：**向量检索能把 84% 拉到多少，值不值它的代价。**

"代价"必须落到具体数字上，不能只说"多个依赖"：模型体积、建索引耗时、
单次查询延迟、`uv sync` 变重多少、CI 受不受影响。

## 1. 前置事实核实（截至 2026-07-27）

两条都影响方案选型，都已核实：

- **Anthropic 不提供 embedding 端点**，官方文档明确推荐 Voyage AI。当前是
  `voyage-4` 系列（32k 上下文、1024 默认维度、支持 Matryoshka 截断）。
  其中 **`voyage-4-nano` 是 Apache 2.0 开放权重**，HuggingFace 可下。
- **DeepSeek 官方 API 文档只有 `/chat/completions`**（`deepseek-v4-flash` /
  `deepseek-v4-pro`），**没有 embeddings 端点**。搜索结果里若干"DeepSeek
  embedding API 已支持"的说法来自内容农场，且与官方 repo 里
  "Embedding-aware API" 至今仍是 feature request 直接矛盾 —— 不采信。

**结论：本工作区现有的两把 key（`ANTHROPIC_API_KEY` / `DEEPSEEK_API_KEY`）
都做不了 embedding。** 这把"本地开放权重 vs 新申请 Voyage key"推到了台前。

## 2. 决定：跑本地开放权重

**选本地，不选 API。** 理由不是省钱，是**保住领域层"零 key"这个性质** ——
ADR-0006 整个架在它上面，`docs/mcp-server-design.md` §1 拒绝在领域层放 LLM 时
算的那三笔账（要 key、每次调用花钱、测试要注入 fake、启动依赖变重），
换成 embedding API 一分不少地全部回来。

本地路线把"纯字面"变成"纯本地"，**ADR-0006 的前提不变**。

代价如实记：多一个 GB 级依赖、首次要下模型、建索引要跑一遍。§5 会把它们量化。

**模型先用 BGE-M3**（C-MTEB 中文检索上口碑最稳）。模型名做参数，换
`Qwen3-Embedding-0.6B` 或 `voyage-4-nano` 是一行改动。

> 时效性标注：BGE-M3 与 Qwen3-Embedding 的对比数据来自中文技术博客
> （CSDN / 知乎，中等可信）。**真正算数的是本项目自己那 22 条 ground truth**
> —— 这也正是这个实验存在的理由。

## 3. 分层：`Embedder` 协议，依赖注入

复用 `judges/` 已经验证过的手法。

```
serve/embedding.py    Embedder 协议 + BGEEmbedder 实现  ← 唯一 import 模型库的地方
serve/query.py        向量打分路径，只依赖协议           ← 不 import torch/transformers
```

关键性质：

- **领域层的 55 条测试注入假 embedder**（确定性向量），零依赖、零下载、毫秒级。
  **"全可测"原样保住** —— 这是本设计不肯让步的一条。
- 只有 `scripts/eval_diagnosis.py --scorer vector` 加载真模型。
- `sentence-transformers` 进 `[project.optional-dependencies]`，
  `uv sync` 默认不拉 GB 级依赖，CI 不受影响。
- **MCP server 默认仍走字面检索**，向量是显式开关 —— 实验期间生产路径不动。

接口草图（实现时以 TDD 为准，此处只定形状）：

```python
class Embedder(Protocol):
    def encode(self, texts: list[str]) -> list[list[float]]: ...
```

单方法协议：假实现好写，真实现是 `SentenceTransformer.encode` 的一层薄包装。
query/document 的不对称（若模型需要 instruction 前缀）在实现内部处理，
不外泄到协议 —— 否则领域层就得知道模型的脾气。

## 4. 受控：只动一个变量

**打分的聚合结构一行不改。** 仍然是：

- 误概念：statement 为主、probe / correction_hint 为次（`SECONDARY_WEIGHT`）
- 知识点：name 为主、description 为次（`DESCRIPTION_WEIGHT`）
- 任一字段过门槛即入选，加权分只用于排序

**唯一被替换的是 `_relevance(Q, T)` 的内部** —— 从"双向 gram 覆盖率取大者"
换成"余弦相似度"。

这条是本设计的核心纪律：这样跑出来的差值**可归因**。若连聚合逻辑一起改，
涨的分说不清是向量的功劳还是新聚合的功劳 —— 那就又造出一个"看起来在量 A、
其实在量 B"的度量，正是上一轮踩过的坑（63% 那次）。

## 5. 阈值怎么定 —— 最容易自欺的一步

余弦相似度与覆盖率标度完全不同，`MIN_RELEVANCE = 0.2` 不可能平移过去。
而**重新挑一个阈值让它刚好越过 75% 闸门，就是自欺**。

做法定死：

1. **扫描阈值，画出完整前沿**（recall@3 × 空样本正确率），不只报一个点。
2. 在**空样本正确率 = 100% 这个相同工作点上**比较两者的 recall@3。
   字面基线在该约束下是 **84%**；向量必须在同一约束下报数才算同台。
3. 前沿曲线整条落盘进对比笔记 —— 让"这个方法在别的工作点上什么样"可查，
   而不是只留一个被挑出来的数。

**同工作点比较**是这个实验公平性的全部保障。任何"向量在 A 点、字面在 B 点"
的对比都是耍赖。

顺带回答一个上轮遗留问题：字面匹配实测 **recall@1 == @3 == @5**，
说明它的排序维度是空的。若向量版的 @1 与 @3 拉开差距，说明它真的带来了
排序能力 —— 那会让"给 LLM 三个候选自己挑"这条设计理由第一次真正成立。

## 6. 明确不做（心法②：尽可能久地保持简单）

- **不引向量库。** 64 节点 ≈ 150 条文本，numpy 一次矩阵乘法就出结果。
  在这个规模上 FAISS / Chroma 是纯复杂度，且会让"零依赖"再破一次。
- **不做 chunking。** 误概念本来就是一两句话，切它没有意义。
- **不做 rerank。** 先看 dense 单路够不够；不够再谈，那是下一个受控变量。
- **不做 hybrid（本轮）。** 先拿到干净的"向量 vs 字面"数字，再用数据决定
  要不要融合。直接上 hybrid 会污染对比 —— 涨上去的分不知道该归给谁。

阶段三的这几块不是不学，是**等有数据说明需要它们**再学。否则就是照着
路线图上课，不是被问题逼着上。

## 7. 测试策略

- **领域层（TDD，全部离线）**：注入确定性假 embedder。要覆盖的形状 ——
  向量维度不匹配、空文本、embedder 抛异常、空图、候选全部低于阈值。
- **不测模型质量**：那是 eval 的事，不是单测的事。单测只测"接线对不对"。
- **CI 不加载真模型**：可选依赖不装，向量路径的单测靠假实现照跑。
- **eval 脚本**：`--scorer literal|vector`、`--threshold-sweep`、`--model <name>`。

## 8. 验收判据

**不是"向量赢了"。** 是这四样齐备：

1. 同工作点（空样本正确率 100%）下两条路线的 recall@3 数字
2. 完整的阈值前沿曲线
3. 量化的代价：模型体积、建索引耗时、单次查询延迟、依赖增量
4. 一段诚实结论 —— **包括"向量没赢"或"赢得不够抵代价"这种结论**

第 4 条是重点。这个实验的价值不取决于向量赢没赢，取决于**"纯检索够不够用"
这个问题第二次被数字回答**。若向量明显更好，ADR-0006 该被推翻并重写；
若差不多，那是"简单方案已经够用"的硬证据，比守着直觉强。

## 9. 已知不确定性

- **22 条样本量小。** 任何 ±1 条命中就是 ±5 个百分点。结论要按这个精度说话，
  不要把 84% vs 89% 讲成"显著提升"。
- **ground truth 是我自己写的**，虽然配了防抄检查，但样本的选择偏好仍是我的。
  向量若在某类样本上系统性更好，要先怀疑是不是样本构造带来的。
- **BGE-M3 在"儿童数学错误说法"这种语域上的表现没有公开数据**。
  C-MTEB 的分数来自通用检索任务，未必迁移。
- **模型体积可能是决定性代价**：若 BGE-M3 让 `uv sync` 从秒级变成分钟级、
  仓库开发体验明显变差，那即使召回更高也可能不值 —— 这属于第 8 条第 4 项
  要如实记的内容。
