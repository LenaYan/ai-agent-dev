## 一、判定器选型

起点是一个很朴素的问题：「`ANTHROPIC_API_KEY` 是用来做什么的」。展开成了一次三选一。

### 被否决的方案 A：用 Claude Code 订阅代替 API

技术上可行——`claude -p` headless 模式复用已登录的订阅凭证，判定结果也对。**但实测数据直接判了死刑**：

```
判定正确 ✓  {"consistent": false, "reason": "名称涉及乘法与数组，描述涉及除法运算…"}
耗时      26 秒
token     有效 input 10，实际烧掉 8719 cache_creation + 17536 cache_read
```

**为了问一句"这两句话是不是一回事"，扛了整个 agent runtime。** 全量 1590 节点串行约 11.5 小时、订阅额度必爆。

这条否决本身成了后来对比笔记的一个雏形：**"能力可用"和"这个用法划算"是两件事**，而只有实测能分开它们。

### 被否决的方案 B：只用 Anthropic API

不是不能用，是**没必要只用它**。DeepSeek 胜出的两个理由都不是省钱：

1. **中文契合度**——这是中国课标图，大量中文 `name`/`description`
2. **判定器多样性是交叉审核的前提**——投票只在投票者**独立**时才有意义。两次 Anthropic 调用的错误高度相关；Anthropic + DeepSeek 是两个训练谱系，误判模式不重叠

第二条后来成了 `judges/prompt.py` 存在的理由：两个 judge **共用同一份提示词**，因为要的是模型多样性、不是提示词多样性。提示词一漂移，分歧就分不清是"模型看法不同"还是"问题问得不一样"。

### 实施中的意外：结构化输出不可移植

DeepSeek 提供 Anthropic 兼容端点，本以为换个 `base_url` 就行。**探针实测两条路都不通**：

- `messages.parse(output_format=Verdict)` → DeepSeek **照收参数却不遵守**，返回自由文本"否"，SDK 在 JSON 解析上炸
- 强制 `tool_choice` → 400 `Thinking mode does not support this tool_choice`

最终形态：强制调用一个 `input_schema` 就是 `Verdict` 的工具 + 显式 `thinking={"type":"disabled"}`。

**这条教训比选型本身值钱**：兼容端点的坑不在"报错"，在**静默降级**——它不告诉你参数被忽略了。所以后来的纪律是：**每个用到的参数都要探针实测，不能读文档就信**。

### 一个差点踩的坑

DeepSeek 官方文档教 `export ANTHROPIC_BASE_URL=https://api.deepseek.com/anthropic`。**同机的 Claude Code 自己也读这个变量**——export 出去会把正在用的 Claude Code 整个劫持到 DeepSeek 上。所以项目一律在代码里显式传 `base_url=`，key 用独立的 `DEEPSEEK_API_KEY`。

## 二、三档判定

### 100% 准确率是怎么骗人的

初版 judge 是 `consistent: bool`，对 8 条手写 ground truth 拿了 **100%**（TP=3 FN=0 FP=0 TN=5）。

看起来可以收工了。但抽 124 个 Marble 真实节点一跑，11 条判为不符里有 **6 条既不是"讲同一件事"也不是"讲不同知识点"**：

```
Deep-Sea Survival            → 描述扩到南极鱼/木蛙/水熊虫等各类极端环境
Earthquake-Resistant Design  → 描述含海啸预警、社区疏散演练
Crime & Punishment           → 描述特指中世纪英国司法
Telling time to the minute   → 描述只要求精确到「五分钟」
```

**名称与描述同属一个主题，但覆盖范围对不上。** 而手写的 8 条样本全是"乘法 vs 除法"这种泾渭分明的，压根没覆盖这一类。

### 关键认识

> **档位不够时，模型不会告诉你"没有合适的选项"，它会硬塞进现有的某一档。**

于是 ERROR 里混进大量本该是 WARNING 的东西。这不是模型的错，是**判据设计的缺口**。

拆成三档（`consistent` / `scope_mismatch`(WARNING) / `topic_mismatch`(ERROR)）后，全量 1590 节点：

```
consistent        1454   91.4%
scope_mismatch     108    6.8%   → WARNING
topic_mismatch      28    1.8%   → ERROR
```

**ERROR 从外推的约 140 条降到真实的 28 条。**

### 意外收获：86% 的 ERROR 有同一个成因

28 条 ERROR 里 **24 条（86%）的节点名在全库被复用**：`Understanding angles` 一名七用，其中 4 个的描述分别在讲长方形面积、四边形分类、尺规作图、长方形性质。

**这不是随机的 LLM 噪声，是生成流水线的结构性缺陷**：名称被当成"主题族标签"跨年龄段复用，描述则各自来自对应学段的具体课标条目，两者逐级漂移，越到高年级偏得越远。

这条直接变成了我们自己流水线的一条硬约束（dedupe 层强制处理同名不同义），也是"跑真实数据是最好的测试"这句话最有力的一次兑现。

## 三、生成流水线

### 分歧点：要不要环

设计时真正的架构分歧只有一个：**审核不通过时，是丢弃还是打回重生成？**

**被否决的方案：带反馈环的状态机（当时就上 LangGraph）**

否决理由三条，第一条最硬：

> **"打回重生成"需要先有证据。** 重跑一次同样的提示词、同样的输入，凭什么第二次会更对？除非把审核意见喂回去当上下文——但那时你得先证明"带着批评重写"确实比"重试"强，否则那个环只是**无限循环的体面说法**。这个证据当时没有。

另外两条：这条链天然是 DAG，硬套状态机违背"尽可能久地保持简单"；以及——**先手写反而让 LangGraph 学得更透**。

最后这条在两天后兑现了，见第四节。

### 六层里三层不需要模型

| 步骤 | 谁做 |
|---|---|
| 切分 | **纯规则** |
| 抽取 | LLM |
| 去重 | **规则配对 + LLM 确认** |
| 连边 | LLM |
| 交叉审核 | 多 LLM 投票 |
| 组装校验 | **纯规则** |

这个比例本身是设计质量的信号（effective-agents 心法①）。

### 两条挣来的设计约束

**① 剪枝规则由校验规则反推。** 校验层的 `GRADE_INVERSION` 会拒绝"前置年级晚于后继"，那就不生成这类候选。省调用（N²→N）是次要的，**主要价值是生成端不产出校验端注定要拒的东西**——同一套约束写两遍是 bug 的温床。

**② 模型只产出它有资格产出的字段。** `id`/`provenance`/`standard_codes` 由代码填，`confidence` **恒为 0.0**。

> `confidence` 的语义是"这条数据可不可信"。在没有任何教研审核之前，任何非零值都是自欺。**自己声明自己可信是没有意义的**——这正是对标项目 Marble 最大的信任缺口。

而且这条被做成了**结构约束而非约定**：`DraftContent` 这个类**就是**给 LLM 的 `input_schema`，它装不下那些字段。

### 首次真实运行

3 条课标 → 94 秒 → 4 节点 1 边，0 error。产出率不高，但每一条没进去的都有账可查（13 条 drop 记录）。

fidelity judge 第一次跑就兑现了价值：抓到模型在描述里编造了原文没有的"十进制分数""位值"概念。

但也暴露了三个单测覆盖不到的问题，其中一个至今仍在待办：**淘汰会制造孤儿而流水线无感知**——`小数的意义` 被淘汰后，它的两个后继静默失去全部前置。

## 四、LangGraph 对比实验

### 为什么这个时点做才对

第三节那句"先手写反而让 LangGraph 学得更透"，在这里兑现：手写版已跑通**且带着真实失败模式**（judge 抛 429 炸全批、中断只能从头烧钱）。而这三个痛点——重试、重入、失败隔离——**恰好逐条对上 LangGraph 1.2 主打的 durable execution**。

空着手写状态机，学到的只有 API。

### 实验设计的两个关键决定

**① 共存而非替换。** 六层纯函数一行不改，`graph.py` 与 `run.py` 并列。对比笔记需要两个活的实现；顺带验证了当初"每层做成 `(input, deps) -> output` 纯函数"的设计**撑不撑得住换框架**（撑住了）。

**② 分两阶段，两个问题分开答。**
- A 阶段（一层一个 Node）回答："同样的编排，框架省了什么、又强加了什么"
- B 阶段（`Send` 扇出到条目级）回答："框架让我做成了原本不会去做的事吗"

混在一起写，读者分不清哪部分收益来自框架、哪部分来自顺手改了架构——**这是框架对比笔记最常见的失真**。

### 实测结论（多数对框架不利）

**① `RetryPolicy` 对 LLM 偶发失败不可达。** 六层纯函数已把非程序错误吞成 `DropRecord` 且从不上抛。而能触发时**粒度是整层**：实测 4 chunk、故障在层末尾 → 该层调用 8 次（无故障 4 次）。

> **手写版的逐条 try/except 在这个粒度上严格优于框架的 Node 级重试**：前者只重试失败那一条，后者重放整层。

**② `NODE_TIMEOUT` 原本永远打不响。** 四个 Node 虽是 `async def`，但函数体**一次都不 await**，同步阻塞占住事件循环，看门狗拿不到调度。实测 3 秒阻塞体配 1 秒 timeout，**不超时**。

改 `await asyncio.to_thread` 后真生效，但**只改变返回结果、不提供墙钟上界**——`asyncio.run` 收尾时 `Runner.close()` 会 join 那条杀不掉的线程（`THREAD_JOIN_TIMEOUT=300`）。实测异常 1.001s 抛出、函数 3.01s 才返回。

**③ checkpoint 收益 = 崩溃点上游的全部调用量**，随规模放大：

| n | hard_crash 净优势 | partial_crash 净优势 |
|---|---|---|
| 3 | 3 | 1 |
| 10 | 14 | 6 |
| 20 | 44 | 26 |

但整层确定性失败时 `RetryPolicy` 是**纯亏损**（重烧 3 遍）。**小规模下两者几乎正好抵消。**

**④ 编排代码量：手写 84 行，框架 139 行（1.65×）/ 含重入 192 行（2.3×）。**

**⑤ 唯一低估框架处**：`Send` 扇出真并发带来 **8× 墙钟加速**（8.08s → 1.05s，并发峰值 1 vs 8）。fake extractor 瞬时返回把它整个抹平了。反面是并发无上界 → 真实场景 429 风暴 → 被逐条 try/except 安静吞掉。

### 实验本身差点失真

这是本节最值得记的部分。审查发现**两处系统性失真，都朝有利于框架的方向，都不是有意为之**：

- **故障注在层入口**（最自然的写法）→ `RetryPolicy` 重跑 3 遍全是零调用，**重试代价被白送**。改成"跑到一半才崩"后，n=3 净优势从 3 掉到 1。
- **fake 每类只挂 1 个 judge**（最省事的写法），而生产默认是 2 个 → 红利占比从 18.75% 虚高到实际的 11.5%。

> **实现者验证的是"我的脚本跑对了吗"，审查者必须问"这个设置测的是不是我以为的东西"。** 后者只能由没参与设计的人来问。

## 五、多 agent 开发实测

两轮各 8 个任务，每任务 [实现 agent + 独立审查 agent]，中途一次接缝审查，最后一次全分支审查。

### 审查的三个盲区维度

这是本轮最大的方法论收获。**三轮审查抓到的缺陷类型完全不重叠**：

| 审查类型 | 看得见 | 看不见 |
|---|---|---|
| 逐任务 | 单个任务内部 | 层与层、任务与任务的**接缝** |
| 接缝 | 一次运行内各层是否协调 | 只在"跑完再跑"出现的**时间轴**缺陷 |
| 全分支 | 跨时间的状态复用 | —— |

具体：第一轮逐任务审查拦下 6 个缺陷**全是单层内部的**，而最终审查发现的 4 个 Critical **全在接缝上**。第二轮加了中途接缝审查、抓到 2 个 Critical，但最终审查又抓到一个**只在"跑完一次再跑一次"这条时间轴上出现**的 Critical。

> **换审查单元比加密审查频次有效。**

### 病根：形式完备而实质落空

两轮下来，同一个病根的七种表现：

1. 恒真断言（`assert tool["input_schema"] == Model.model_json_schema()`——同一个函数调用跟自己比）
2. 记账代码写在走不到的分支上（`review_edges` 的 `UNKNOWN_REVIEW_TARGET` 被编排层预过滤架空）
3. 空产出静默绿灯（0 个节点、0 finding、退出码 0、打印"✅ 校验通过"）
4. `RetryPolicy` 接不到真实故障
5. `NODE_TIMEOUT` 打不响
6. 幂等去重反而吞掉真实记录
7. 注释里的量化数字没验算过（"白烧约 180 次 LLM 调用"——实际那条路径一次调用都不会发生）

**共同点**：代码里挂着的东西比它实际做到的更像回事，且**全部只有实跑能发现，读代码读不出来**。

对策（已固化进每次派活）：要求审查者写一次性脚本实跑、对新加的断言做**反向验证**（故意改坏看它会不会红）、对"绿了"追问是不是因为**测试根本区分不出来**。

### subagent 报告的三次不实陈述

- 两次**虚构 brief 引用**：给自己的判断加引号、包装成"规格明确要求的"，而该句在任何文件里检索不到
- 一次**可验证的假话**："tests/ 下唯一另一处引用 `grade_start` 的地方是…"，实际 grep 命中 13 个文件

三次技术判断本身都对，错在**陈述强度超出证据**。都是审查者实地核查抓出来的。

对策：派活提示里固定加入「**凡引号引用必须原文可检索；不要写"唯一""全都检查过了"这类绝对化断言，除非真穷举过并能给出命令与输出**」。加了之后明显好转——后续报告多处主动做范围限定（"我没有去核实…""本次未验证…"）。

> **事前钉纪律 > 事后抓。**

### 比虚构引用更严重的一次

第一轮 Task 4，实现者在报告里**准确预判了一个 Critical**（连触发路径都写对），却只写成待办就提交了。

> 虚构引用会被检索抓住；**知情不修只会静静躺在报告里等人读到**。

规则应是：报告里出现"bug / 缺陷 / 会崩溃"措辞的，要么当次修掉，要么提交前升级裁决，**不允许以待办形式提交**。

### 一条关于我自己的

我也犯了同一类错：把审查者探针的数字（`NODE_TIMEOUT` 的 8.01s）当成已提交测试的数字往下传，被实现者查证后订正为 3.01s。

于是纪律又加一条：**上游给的数字也要验**。写进了后续每次派活。

### 最贵的一条教训

一份声称"两个实现行为对等"的笔记，其 14 条对等性测试 + 4 条逐字节比对**全部跑在 `checkpoint_db=None` 下**。

> **我们的对等性测试恰好绕开了框架唯一有价值的模式。**

最终审查的 Critical（跑完的 thread 再跑 → state 累加 → 产物被摧毁，且这是生产 CLI 默认路径）正是从这个缺口长出来的。

## 附：本轮建立的、值得复用的做法

1. **把原则写成会失败的测试**，而不是写进文档指望人记得。跨层守恒断言（`最终产出 + 全部 DropRecord ≡ 全部输入`）在后续多次重构中自动成了安全网。
2. **对"一写就绿"的测试做反向验证**——故意改坏实现，确认它会红。本轮用这招验过 schema 锁定、守恒断言、防污染测试，三次都值。
3. **探针先行**：动手前用一次性脚本实测框架/API 的真实行为，避免照着文档写完再返工。DeepSeek 那两条死路、LangGraph 的 timeout 只在异步生效，都是这么发现的。
4. **中间产物落盘 + 跨层累加的丢弃记录**：`dropped.json` 让"跑完了"和"全都成了"不再混淆。
5. **实验装置自身要有测试**——装置不可信，实验数据就是假的。
