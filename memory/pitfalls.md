## 新写的测试一次就全绿，其中一条在守一个它根本没在守的东西  (2026-08-05)
- **现象**：给误概念漂移度量写了 15 条测试，第一次跑全绿。其中 `test_two_before_statements_cannot_both_claim_one_after_statement` 用来守"贪心一对一"约束：两条旧 statement 不许双双认领同一条新 statement。它是绿的。
- **根因**：第二条 fixture（"减法也是有交换律的" vs "减法应该也有交换律"）的字面分只有 **0.50**，低于配对门槛 0.6。它被**阈值**挡在外面，跟一对一约束一点关系都没有。**把一对一约束整个删掉，这条测试照样绿。**
- **怎么发现的**：不是靠读代码，是**把 fixture 的实际分数逐条打印出来** —— 与"每次都把明细逐条打出来看"是同一个动作，只是这次对象从数据换成了测试夹具。
- **解法/规则**：① 断言型测试要配一次**变异测试**（把被守的那行改坏，确认它变红）—— 本例删掉 `j in taken` 后该测试立刻失败，形状才对；② 依赖"分数落在某区间"的 fixture，**把前置条件也写成断言**（`assert all(relevance(...) >= THRESHOLD)`），换 fixture 时它会替你抓住这种退化，而注释不会；③ **"新测试一次全绿"本身是个信号**，尤其是判据依赖阈值/相似度这类连续量的时候 —— 全绿可能是写对了，也可能是每条都从旁边绕过去了。

## 一份"两个实现行为对等"的逐字节比对，看不见只接在其中一个实现上的新功能  (2026-07-29)
- **现象**：稳定 id 注册表接在手写引擎（`run.run_pipeline`）里，两个 LangGraph 引擎共用的 `graph.node_assemble` 调 `assemble` 时**没传 registry**，静默退回 `sha1(name)`。而项目里有一条专门为此存在的测试 —— 逐文件逐字节比对两个引擎的**全部**产物（`test_two_engines_produce_identical_artifacts_on_normal_run`），它是绿的。
- **根因**：**注册表在首轮是空的，认领不到任何条目，于是两条路径给出的 id 恰好逐字节相同。** 差异要到第二轮才现形（注册表根本没落盘，同义改写照样换身份）。那条比对测试只跑**一轮**，而这个功能的全部价值都在**跨轮**。
- **可推广的规则**：**跨实现的对等性测试，射程止于它跑的轮数。** 凡是"状态跨运行累积"的功能（注册表、缓存、增量索引、去重记账），对等性必须**跑两轮**才谈得上验证 —— 第一轮的空状态是最容易骗过比对的形状。
- **解法**：补 `test_synonymous_rename_keeps_topic_ids_across_reruns` —— 跑两轮、中间把节点名做同义改写、断言 id 不变，三个引擎各一份。RED 时手写版通过、两个 LangGraph 引擎全挂，形状正确。**顺带一条**：这个功能此前连手写引擎那侧也没有集成测试（只有 `topic_registry` 的单元测试），所以缺口不是"漏接了一个引擎"，是"接线本身从没被测过"。

## 提高"标签存活率"的办法里，最有效的那个是把标签挂错地方  (2026-07-29)
- **现象**：重跑流水线后 17 条评测样本死了 8 条锚点。想到一个办法：用旧图的节点**种子化**稳定 id 注册表，让新图去认领旧身份。离线干跑：45 个认领，标签存活 9/17 → **14/17**。
- **根因**：多出来的 5 条里有 3 条来自一个**假合并** ——「小数的意义」→「万以内数的意义」，靠共有的"数的意义"把名称相似度顶到 0.750，学段区间又恰好重叠，合成分 **0.604**，只高出门槛 0.004。那三条小数样本会被挂到一个**讲整数**的节点上：指标变好，标签变错，而且**不报错**。
- **一句话**：**"只看存活率会选出错误的方案"这条教训，是上一轮定 id 方案时刚写下的，换个场景（种子化）立刻又踩一次。** 教训写在文档里不等于会在下一个决策点自动触发 —— 它触发的方式是**每次都把明细逐条打出来看**，而不是看汇总数字。
- **解法/规则**：① 凡是"提升某个存活/命中/通过率"的改动，**验收必须逐条列出新增的那几条是怎么来的**，不能只比总数；② 描述相似度 0.265 本来是一张诚实的反对票，被 0.7 的名称权重压过去了 —— **当一个信号被权重压过去时，问题多半在判据的构成，不在阈值的取值**（把门槛从 0.6 提到 0.62 只挡得住这一个，挡不住 0.682 那个）。
- **备注**：`CLAIM_THRESHOLD = 0.6` 的"0 假合并"读数是在**三次同管道运行**上量的，那个射程内仍然成立；一旦跨越更大的名称集变动（66 → 78 节点），45 个认领里就出现 2 个假合并。**校准值要连校准条件一起引用。**

## 统计谦逊只用在"结果"上，没用在"判据"上 —— 那个保证公平的指标，分母只有 3  (2026-07-28)
- **现象**：一个受控对比（字面 vs 向量检索）的公平性，整个压在一条纪律上——"不许各挑各的阈值，必须在**空样本正确率 = 100%** 这个相同工作点上比 recall@3"。纪律执行得很严，结论也写得很谦虚（对 recall@3 那 19 条反复算 ±1 条 ≈ ±5.3pp、算 McNemar、拒绝说"显著优于"）。**但把用来锚定工作点的那个指标的样本从 3 条补到 11 条之后，每一个基线数字都变了**：生产阈值的空样本正确率 100%→91%、字面工作点 0.15→0.25、基线 89%→79%、向量 0.7→0.75、79%→53%、差距 10pp→26pp。
- **根因**：那 3 条恰好都是"完全不相关"的容易样本（几何、钟表、背古诗），任何方法只要对这三类说得出"不知道"就拿到 100%，就被判定"站在了公平的起跑线上"。**而那把统计谦逊的尺子一次也没量到它身上——因为它当时不被当成"结果"，而被当成"实验装置的一部分"，而实验装置是不会被审的东西。**
- **一句话**：**纪律守住了"不许作弊"，守不住"指标本身没意义"。** 这是"小样本上的百分比要当心"第一次不是发生在被比较的对象身上，而是发生在**裁判身上**。
- **解法/规则**：① **凡是用来定义工作点 / 闸门 / 判定标准的指标，必须和被测指标受同等审查** —— 对它问同一个问题："分母是几？±1 条会让它跳多少？"；② 判据类样本必须**覆盖多个互斥类别**，不能全是同一种容易样本（本例补样本按"其他领域 / 完全非数学 / 太笼统"分三类，才第一次逼出生产阈值上那条相关度 0.2105 的误招）；③ **先定分类、按分类把样本写死、写完才第一次跑分数** —— 反过来做（跑一遍看谁漏了再补）就是拿被测系统的输出去设计测它的集合，得到的 100% 什么也不说明。
- **反直觉的一条**：**差距变大不等于证据变强。** 10pp→26pp 之后仍然是 n=19、一条样本值 5.3pp；变结实的是判据的分辨率，不是那个差值。差距变大最容易诱发的动作就是把话说满。
- **备注**：详见 `practice/cn-curriculum-graph/docs/rag-vs-literal.md` §6.0。**结论方向没变（向量仍然没赢）是运气，不是纪律给的保证。**

## 装个本地 embedding 模型：进程跑完结果全打印完了，就是不退出  (2026-07-27)
- **现象**：`uv run python scripts/eval_diagnosis.py --scorer vector --threshold-sweep` 把完整前沿全部打印完之后**进程不退**，实测卡 **9 分 50 秒**才 `EXIT=0`。CPU 时间只有 12.5s，而墙钟 9:50 —— 一看就不是在算。
- **根因（两层）**：① `BAAI/bge-m3` 主分支只有 `pytorch_model.bin`，`transformers` 5.x 会**在后台线程里从仓库的 PR 分支 `refs/pr/130` 另抓一份 `model.safetensors`**（于是 2.2G 的模型实际落盘 **4.3G**，缓存里能看到第二个独立 snapshot 目录）；② 那个下载线程是 **非 daemon** 的，`Py_FinalizeEx → wait_for_thread_shutdown` 会一直等它。我第一次跑被超时杀掉，缓存里留下 `*.incomplete` 分片，`hf_xet` 线程就一直卡在 `_dispatch_semaphore_wait_slow` 里重试。
- **解法**：`find ~/.cache/huggingface -name "*.incomplete" -delete`，同一条命令随即 **27.1s 干净退出**。
- **诊断动作（可直接复用）**：进程"卡住"时先比 **CPU 时间 vs 墙钟时间**（`ps -o time,etime`）——差得远就不是在计算，是在等。然后 macOS 上 `sample <pid> 3 -f out.txt` 直接抓栈，看主线程是不是停在 `Py_FinalizeEx`；**停在那里就等于"有个非 daemon 线程没结束"**，去下面的线程列表里找那个还在 wait 的。不用装 py-spy。
- **备注**：`huggingface-hub` 1.25 / `hf_xet` 1.5 / `transformers` 5.14 / `sentence-transformers` 5.6，2026-07-27。这不是本项目的 bug，但它是"多一个 GB 级依赖"这句话的真实展开 —— **可选依赖的代价从来不止 `du -sh`**。

## 声称"扫过全档"之前，先看一眼自己到底扫了哪几个点  (2026-07-27)
- **现象**：memory 里躺着一条结论"扫过全档阈值确认：单纯调阈值只是在'召得回'与'敢返回空'之间沿同一条前沿滑动，换不来净收益"。它被当成既定事实引用了整整一轮，还写进了代码注释。
- **真相**：真正跑一遍 0.05–0.95 步长 0.05 的完整前沿后，**阈值 0.15 同时拿到 89% 召回和 100% 空样本正确率**，比生产默认值 0.2（84%）净高 5 个百分点。上一轮大概率只扫了 0.1 和 0.2、跳过了 0.15，于是把"我没扫到"写成了"不存在"。
- **附带伤害**：那条错误结论顺手固化了一个**偏低的基线数字 84%**，而真基线是 89%。**基线偏低是最危险的一种错误** —— 它会让后来任何新方案（本例是向量检索）凭一个被压低的基准"赢"，而且赢得很有说服力。
- **解法**：① 结论里带上**实际扫描的点列**，不要只写"全档"；② 把扫描做成可复跑的脚本 + 落盘的前沿表，而不是一次性的手工试；③ 引用别人（或过去的自己）的基线数字前，先确认它是在**哪个工作点**上读的。
- **要点**：**"没有净收益"和"我没找到净收益"是两句话。** 前者需要穷举，后者只需要偷懒。写记忆的时候很容易把后者写成前者。
- **[2026-07-28 更正：这条"真相"自己也没活过一天]** 上面那句"阈值 0.15 同时拿到 89% 召回和 **100% 空样本正确率**"里，那个 100% 的**分母只有 3**。空样本补到 11 条后，0.15 的空样本正确率是 **91%（10/11）**，够不到工作点；真正的同工作点右移到 **0.25**，字面基线是 **79%**。所以"真基线是 89%"也作废 —— **基线被同一个坑更正了两次**。新规矩：**引用基线必须连工作点一起写**（"79% @0.25，同工作点口径"），光写百分比不算数。这条坑的下半场见下一条。

## LLM 判定器"淘汰率异常高"时，先看分歧率再改 prompt  (2026-07-27)
- **现象**：二值 fidelity 判定淘汰了 62% 的产出，图稀疏到没法用。第一反应是"prompt 写得不好"或"标准太严"。
- **真相**：45 条淘汰里 **21 条（47%）是分歧淘汰**——两个模型看法相反，且**方向随机**（同类样本上 A 判过 B 判否，换个样本反过来）。这不是标准松紧问题，是**判定档位不够**：模型面对"没有合适选项"时不会告诉你，它会硬塞进现有某一档，塞哪一档是随机的。
- **解法**：加档，不是调 prompt。二值 → 三档后误杀 45→0。
- **诊断动作（可直接复用）**：逐票统计而不是逐结论统计。`Counter(tuple(v['approved'] for v in outcome['votes']))` 一行就能把"都否 / 分歧"分开。**分歧率高 = 档位不够；一致否决率高 = 标准或 prompt 问题。** 两者的修法完全不同。
- **陷阱**：读 outcome 时别只打印 `votes[0]` —— 全票通过才算过，`votes[0]` 完全可能是赞成票，会让你误以为"模型的理由和它的投票自相矛盾"。我踩过一次，差点据此做了错误的重构。
- **反直觉的一条**：为压掉漏报加针对性规则，**实测让漏报变多**（2→3）——规则把模型注意力全引向"多写"，挤掉了"少写（内容缺失）"。判定质量不是加规则就单调上升的；每加一条都要跑 ground truth，别凭感觉。

## 判定器的闸门要按代价不对称定，不是按准确率  (2026-07-27)
- **现象**：三档 fidelity 评测 17/20 = 85%，"误杀 0、漏报 2"。按"准确率 ≥90% 才算过"这种闸门会判失败，然后就会去调 prompt 追那 15%。
- **问题**：85% 这个数字把两类方向相反的错误混成了一个标量。实际代价差一个数量级——**误杀**（合格被淘汰）让图稀疏到没法用，已实测；**漏报**（编造被放行）只是让个别节点混进一张 `review_status=unreviewed` / `confidence=0.0` 的图，而那正是 provenance 诚实性设计要兜的场景。
- **解法**：闸门按方向分级，不看总准确率。误杀非零即红；漏报**记显式基线**（当前 2）、变差才红。基线写进代码注释并说明每条为什么压不掉（其中一条根因在上游抽取层，不在判定器）。
- **要点**：基线是**已知限制的显式记录，不是目标**。把它调低要靠证据，不是靠调低期望。

## "需要全局视野"不等于"必须串行"  (2026-07-27)
- **现象**：`review_edges` 一直是串行的，理由是"它需要全局 kept_ids"。真实语料上量后变成 690 次串行 LLM 调用，撞上 10 分钟 node timeout，总耗时 49:32。
- **原因**：把两件事混为一谈了。它需要全局视野才能**开始**（要先知道哪些 draft 活着），但开始之后**每条边的判定彼此独立**。"需要全局视野"阻止的是**扇出**（把任务 Send 到条目级、由编排层调度），**不是层内并发**。
- **解法**：函数内部开线程池并发，对外仍是同步函数。49:32 超时 → 2:27。
- **推论**：**"并发上限校准好了"不等于"整条流水线都并发了"**。校准只覆盖了编排层的两个扇出点，`review_edges` 和 `dedupe` 从来没被并发化——只是以前它们没活干，所以没人发现。上游一改（判定放宽、存活率上升），瓶颈立刻转移到没人看的那一层。
- **并发化一个既有纯函数必须守住的三条**：①**产物顺序须与串行完全一致**（若有逐字节比对产物的对等性测试，完成顺序泄漏进排列会让它变成随机红绿，比慢糟糕得多）；②**异常须在工作线程就地转成返回值**（`executor.map` 是惰性的，一旦某任务抛出，它之后的结果就取不到，"单条失败不中断整批"会静默失效）；③**程序错误须显式还原类型再 raise**（线程池会包装异常，`except PROGRAMMING_ERRORS` 那道防线在并发路径上否则失效）。

## 教育部课标 PDF 是扫描件，pdftotext 提不出字  (2026-07-27)
- **现象**：`http://www.moe.gov.cn/srcsite/A26/s8001/202204/W020220420582346895190.pdf`（义务教育数学课程标准 2022 年版，40MB / 189 页）下载正常，`pdftotext -layout` 输出 0 行。
- **原因**：扫描件。`pdfinfo` 显示 `Producer: Adobe Acrobat 18.11 Image Conversion Plug-in`，`pdffonts` 输出空 —— 没有文字层。
- **解法**：OCR，或用支持视觉读 PDF 的工具逐页转录。小学·数与代数【内容要求】在正文 p.17–26（三个学段共 28 条），PDF 页码 ≈ 正文页码 + 7。
- **顺带**：`pdffonts` 输出为空是判断"扫描件 vs 文字版"最快的一招，比试着提取再看结果快。

## LangGraph：只把 serde 改严格，反而比不改更糟  (2026-07-27)
- **现象**：为了提前适配"未来版本会强制拦截未注册 msgpack 类型"，把 checkpointer 的 serde 换成严格模式（`JsonPlusSerializer(allowed_msgpack_modules=())`）。改完 happy path 全绿，但**崩溃后 checkpoint 续跑当场炸** `AttributeError: 'dict' object has no attribute 'draft_id'`。
- **原因**：langgraph（1.2.9）里这是**两个独立开关**——(a) 序列化器严不严格，由你传的 `allowed_msgpack_modules` 决定；(b) 要不要**自动从 state schema 推导 allowlist**，由 `StateGraph.compile()` 里的 `if _serde.STRICT_MSGPACK_ENABLED:` 决定，而这个常量是 import 时从环境变量 `LANGGRAPH_STRICT_MSGPACK` 读死的。四种组合里 `严格 serde + 未设环境变量` 是陷阱格：严格拦截照常生效，推导整个跳过 → 所有自定义类型的 allowlist 为空。
- **解法**：不依赖环境变量，自己调 `langgraph._internal._serde.build_serde_allowlist(schemas=[...], channels=...)` 再 `saver.with_allowlist(...)`。（用了私有 API，配一条测试当绊线，升级时先红。）
- **额外要记住的**：未注册类型的失败模式**不是拒绝，是静默降级成 dict**（ext hook 拒绝时 `return tup[2]` 返回该模型的 kwargs）。所以症状永远出现在**下游业务代码**上，看起来像业务 bug——**续跑路径上遇到莫名其妙的 `'dict' object has no attribute ...`，先查序列化配置，别去 debug 业务逻辑。**
- 备注：langgraph 1.2.9 / langgraph-checkpoint 4.1.1。另：`compile(checkpointer=saver)` 返回的是带 allowlist 的**克隆**，直接拿原 saver `aget_tuple()` 会看到降级后的 dict——这个不一致是设计如此，曾把我们误导过一轮。

## `asyncio.to_thread` 有一道隐藏并发天花板  (2026-07-27)
- **现象**：把并发上限从 8 调到 32，实测在飞峰值只有 20，吞吐不再增长、p95 反而翻倍。
- **原因**：`asyncio.to_thread` 用的是事件循环的**默认 executor**，CPython 的 `ThreadPoolExecutor` 默认 `max_workers = min(32, os.cpu_count() + 4)`。信号量放行再多，多出来的只会排队。
- **解法**：并发上限默认值直接取 `min(32, cpu_count+4)`（写成公式，别抄某台机器上的具体数字）；要真正提高必须先 `loop.set_default_executor()` 换更大的池。设置超过这道墙时**发警告而不是静默截断**——否则现象是"我明明调到 64 了怎么没变快"，代码里没人告诉你原因。
- **值得记住的因果**：这道墙常常是**自己引入的**。本项目是为了让 LangGraph 的 per-node `timeout` 生效，必须把阻塞的 SDK 调用改成 `await asyncio.to_thread(...)`——超时能力和并发天花板是同一个决定的两面。
- 备注：另一半认知修正是 provider 侧——DeepSeek 不设 RPM/TPM，只设**账户级并发连接数**（v4-flash 2500 / v4-pro 500，超出返 429），所以"为了不撞限流而调低并发"这个直觉在它身上基本用不上。

## 概念辨析纠偏：社区资料常见的 5 处错误  (2026-07-06)
来源：一份社区「7 种 Agent 架构」分享，与 Anthropic 一手资料/官方文档核对后纠正。
- **ReAct 全称**：是 Reason + **Act**（Reasoning and Acting），不是「Reason + Actor」。
- **LangGraph ≠ DAG**：它支持**环（cycle）**可循环回退，正是区别于 Airflow/Prefect 纯 DAG 引擎之处；说它「基于有向无环图」是错的。
- **LangGraph ≠ Blackboard**：LangGraph 是图/状态机编排；Blackboard 是「共享知识库 + 机会式读写」的经典范式，二者机制不同。
- **Airflow / Prefect / n8n 不是 agent 框架**：它们是通用数据/任务流水线或低代码自动化，别和 LangGraph 混为一类。
- **Router+Skill 不是 AI Coding「唯一最佳实践」**：主流 AI coding agent（Cursor/Claude Code/Copilot）更多是单 Agent + 丰富工具 + 强上下文工程；Router+Skill 只是可靠性收益高的一种模式。
- 备注：判断架构别按「1→7 进化线」，按三正交维度（推理范式/协作拓扑/编排基础设施）选。详见 docs/agent-architecture-patterns.md。

## 2026-07-24 — 按单一 key 分组做报告会把高严重级藏进低严重级
- 坑：格式化校验报告时按 `code` 分组，用 `group[0].severity` 决定整组的显示标记。同一 code 严重级可能不同（GRADE_INVERSION 在 hard 边是 ERROR、soft 边是 WARNING），结果 7 条 error 被显示成 warning 组，CI 看起来像只有警告。
- 解法：按 `(code, severity)` 复合键分组。
- 教训：分组键必须覆盖所有影响展示的维度。单测没抓到（测试数据同 code 同严重级），是跑真实数据才暴露的。

## 检索评测跑出低分，第一件事不是换模型，是确认度量在量什么  (2026-07-27)
- **现象**：诊断检索首跑 recall@3 = 63%，闸门红。设计文档里预留的分叉写着"可能是纯检索不够用 → 考虑引入 LLM"。
- **真相**：逐条看未命中样本，掉的两件事都跟语义理解无关。①**长度惩罚**：打分只算"查询被覆盖了多少"，分母是整句，家长的具体转述越啰嗦越吃亏，真正对上的词被"他说""一样"稀释到门槛以下。②**表示层不同**：图里写 `1/4`、`5-3=3-5`，家长说"八分之一"、"5 减 3"，字面重叠是零 —— 不是同义词问题。
- **解法**：两个方向的覆盖率取大者 + 数学表达归一化（只在数字之间改写运算符，否则"减法"会变成"-法"）。63% → 84%，**阈值一个数没动**。
- **教训**：照着"低分 → 上模型"的剧本走，等于用一个模型去补一个除法写错了分母的窟窿。**先看未命中样本，再看指标。**

## IDF 加权在"用户口语 vs 语料"的匹配上会反向发力  (2026-07-27)
- **现象**：想用 IDF 压掉长查询里的噪声词，实测 recall 63% → 53%，更差。
- **原因**：IDF 度量的是"**在语料里**罕见"。用户口语里的噪声（"他说""一样"）恰恰在领域语料里从没出现过，df=0 → 权重取到最大，把分母顶得更高。**要压的词反而被加权了。**
- **解法**：这个场景不要 IDF。改用双向覆盖率（max(查询被覆盖比例, 目标被覆盖比例)），无 IDF 反而更好且少一层"加节点会改变已有分数"的耦合。
- **备注**：适用范围是"查询与语料来自不同语域"（口语 vs 书面、外行 vs 术语）。同语域检索里 IDF 仍然有效。

## MCP server 的 cwd 由客户端决定，默认路径不能写成相对 cwd  (2026-07-27)
- **现象**：本地 `uv run` 起 server 一切正常，但配进客户端后会以一句 `FileNotFoundError` 起不来。
- **原因**：stdio server 的工作目录由启动它的客户端决定，不是你 `cd` 过去的那个目录。
- **解法**：默认数据路径相对**包位置**解析（`Path(__file__).resolve().parents[N]`），并补一条 `assert DEFAULT_PATH.is_absolute() and .exists()` 的测试钉住。环境变量覆盖仍然保留。

## 跨运行的数字对比之前，先证明流水线是可复现的  (2026-07-28)
- **现象**：修完边审核的输入 bug 后重跑流水线，边 31→162（真改进），但检索 recall 在同工作点上从 79% 掉到 59%。看起来像"边好了、检索差了"的取舍。
- **真相**：同一份原文、同一套代码、四层全 `temperature=0`，跑三次得到三张对不上的图 —— 两两节点名 Jaccard 只有 **29%~52%**。那 17 个百分点里有多少是改动的效果、有多少是抽签，**说不清**。
- **动荡的成分**：①28 个 chunk 里 **8 个（29%）至少一次颗粒无收**，每次是不同的几块（落在 dropped.json 的 `NO_DRAFTS` 里，留痕了但没人读）；②三次都有产出的 chunk 里只有一半名称一致，而"消失"的名称里 **64%~80% 其实是同义改写**（"计数单位的感悟"→"计数单位"、"了解十进制计数法"→"十进制计数法"）。**内容是稳的，抖的是措辞。**
- **放大器**：`make_topic_id = sha1(name|domain|grade_start)`。它的 docstring 写明防的是"增删条目导致序号平移"，**而现实中占主导的是改写** —— 为一种威胁做了防护，撞上的是另一种。名字删两个字，id 就变，评测标签全死（24 个里死 12 个）。
- **单次调用其实相当稳**：同一 chunk 连发三次，名称集合多数完全一致，只有误概念文本在变。所以不是"模型完全随机"，是**措辞与切分粒度处在浅势阱里，同会话内一致、跨会话会漂**。
- **射程**：字面 vs 向量那轮**不受影响** —— 它把图固定住只换打分器，是干净的单变量对比。被推翻的是任何**跨重跑**的指标比较。
- **要点**：**任何"改了 X 之后指标变化 Y"的结论，都欠一个前提：这条流水线跑两次给出同一个结果吗？** 这个前提直到今天才第一次被验证，而它不成立。详见 practice/cn-curriculum-graph/docs/pipeline-reproducibility.md。
