# Agent 架构模式目录（Pattern Catalog）

> 编写日期：2026-07-06 · 用途：学到某阶段时查对应模式的**参考手册**，不是学习顺序。
> 本文档是对一份社区分享「7 种 Agent 架构」的**修正与重构**：保留其好记的结构，纠正事实错误，并补上诚实的取舍与选型指引。

---

## 0. 先破一个误区：这不是一条「进化线」

常见的错误框架是把这些模式排成「1→7 由低级到高级」，暗示编号越大越先进、多 Agent/图工作流是「终极形态」。**这是误导。**

真实情况：这些模式分属**三个正交维度**，不是一条线。

| 维度 | 回答的问题 | 属于它的模式 |
|---|---|---|
| **A. 单 Agent 推理范式** | 一个 agent「怎么想」 | 单 Agent · ReAct · Plan & Execute · Reflection |
| **B. 多 Agent 协作拓扑** | 多个 agent「怎么配合」 | 多 Agent 编排 · Blackboard |
| **C. 编排 / 基础设施** | 用什么「引擎」把流程跑起来 | Graph / Workflow |
| **× 路由模式（跨维度）** | 先「选」再「做」 | Router + Skill（可套在任意层之上） |

### 行业主流原则：**简单优先（Simplicity-First）**

来自 Anthropic《Building Effective Agents》等的共识：

> **从最简单的方案开始，只在「简单方案确实不够」时才增加复杂度。**

推论：
- 多 Agent **不是**比单 Agent「更高级的进化」——它常常**更贵、更不稳、错误率更高、更难 debug**。
- 很多顶级生产系统（含主流 AI coding agent）是 **单 Agent + 丰富工具 + 强上下文工程 + 工作流编排**，而不是一堆 agent 互相喊话。
- 复杂度是**成本**，不是**成就**。加复杂度前先问：简单方案哪里不够？

## 维度 A：单 Agent 推理范式

### A1. 单 Agent（Single Agent + Tools）
- **机制**：一个 LLM 负责全部决策，可调工具/API/数据库，带简单记忆。用户输入 → LLM 思考 → 调工具 → 输出。
- **优点**：简单、便宜、易调试、易治理。
- **问题**：任务一复杂就「思考爆炸」、上下文污染、并发多任务时混乱。
- **适用**：ChatGPT 类助手、简单自动化、单一职责任务。**应作为你的默认起点。**

### A2. ReAct（Reason + Act）
- ⚠️ 全称是 **Reasoning and Acting（推理 + 行动）**，不是「Reason + Actor」。出自论文 *ReAct: Synergizing Reasoning and Acting in Language Models*。
- **机制**：循环「思考 → 行动（调工具）→ 观察结果 → 再思考」，直到完成。
- **优点**：推理链完整、可解释、能处理多步任务。是大多数 agent 循环的雏形。
- **问题**：token 消耗大、不稳定、易跑偏；纯 ReAct 不适合大规模工程化。
- **适用**：复杂问答、多步任务、探索/原型阶段。

### A3. Plan & Execute（先规划后执行）
- **机制**：Planner 先产出完整计划（步骤 1/2/3…），Executor 按步执行。
- **优点**：更工程化、稳定、适合长流程。
- **问题（修正）**：计划出错**不必然**全盘崩溃——成熟实现有 **replanning / 反思纠偏**。真正的弱点是「前期规划 vs 边做边调」的灵活性权衡。
- **适用**：代码生成、项目自动化、长流程任务。

### A4. Reflection（自我反思，原分享漏了但很重要）
- **机制**：agent 产出后自查、批判、迭代改进（self-critique）。
- **常与 A2/A3 组合**，用少量额外 token 换质量。
- **适用**：对正确性要求高的生成任务（代码、报告）。

> 组合关系：A2/A3/A4 常叠加使用（如 ReAct + Reflection），不是互斥选项。

## 维度 B：多 Agent 协作拓扑

> ⚠️ **进入前必读**：多 Agent 是把「双刃剑」。默认**不用**，除非任务**高度可并行 / 跨专业域 / 需隔离上下文**。多 Agent 常增加协调开销、上下文不一致、成本翻倍、debug 困难。别因为「听起来高级」就上。

### B1. 多 Agent 编排（Orchestrator + 专职 Agent）
- **机制**：Orchestrator 拆解并分派任务给专职 agent，如 Planner / Coder / Reviewer / Tool Agent。
- **优点**：职责清晰、隔离上下文污染、可扩展。
- **问题（需加重）**：协调复杂、成本高、错误会跨 agent 传播、整体可靠性不一定比「单 Agent + 好工具」高。
- **适用**：真正需要多专业分工、可并行的复杂项目/企业级场景。

### B2. Blackboard（黑板系统）
- **机制（澄清）**：经典 AI 范式——多个 agent 共享一块「黑板」（共享知识库/状态），**机会式**地读写，状态变化驱动谁该行动。更接近共享内存 + 事件驱动。
- **优点**：适合松耦合、涌现式协作。
- **问题**：状态管理复杂、竞态、出问题难追踪。
- **适用**：复杂协作、需要共享演进状态的场景。
- ⚠️ **纠正**：Blackboard ≠ LangGraph。LangGraph 是「图/状态机编排」，不是经典黑板；把二者划等号是分类错误。（LangGraph 的共享 State 有点黑板味道，但机制不同。）

## 维度 C：编排 / 基础设施

### C1. Graph / Workflow（图/工作流编排）
- **机制**：把流程建成图（节点=步骤，边=流转），支持条件分支、并行、回溯、可观测、重试。
- **优点**：企业级稳定、可 debug、支持长流程与人在环。
- **适用**：生产环境、长流程自动化。
- ⚠️ **两处纠正**：
  1. **LangGraph 不是 DAG**：它的核心卖点是**支持环（cycle）**，能循环回退——这正是它区别于纯 DAG 引擎之处。说「基于有向无环图」是错的。
  2. **别把 agent 框架和通用流水线引擎混为一类**：
     - **Agent 编排框架**：LangGraph（支持环、为 agent 设计）
     - **通用工作流/持久化引擎**：Temporal（持久化工作流）
     - **数据管道编排器**：Airflow、Prefect（DAG、批处理，**不是 agent 框架**）
     - **低代码自动化**：n8n
     它们能配合 agent 用，但不是同一层的东西。

## 跨维度：Router + Skill（路由 + 技能）

- **核心理念**：**「不让模型『想』，而让模型『选』」**——用意图路由把请求分派到预定义的确定性 Skill。
- **机制**：用户输入 → Intent Router（意图识别）→ 命中对应 Skill 执行。
- **优点**：稳定性强、可控、可缓存（性能高）、命中率易评估。
- **问题**：Skill 设计/维护成本高、意图冲突/边界模糊、覆盖不到的长尾请求需兜底。
- **适用**：意图**明确、可枚举**的系统（客服、固定技能助手）。
- ⚠️ **纠正过度断言**：说它是「AI Coding 最佳实践、大多采用」**过头了**。当下主流 AI coding agent（Cursor / Claude Code / Copilot）更多是**单 Agent + 丰富工具 + 强上下文工程**，而非死板的意图路由+技能表。Router+Skill 是**可靠性收益高的一种模式**，但不是唯一或必然选择；它还能叠加在单/多 Agent 之上（跨维度）。

## 选型速查

| 场景 | 建议起点 |
|---|---|
| 快速验证 / 简单任务 | 单 Agent（A1） |
| 多步骤、需推理链 | ReAct（A2），必要时加 Reflection |
| 长流程、要稳定 | Plan & Execute（A3）+ replanning |
| 意图明确可枚举 | Router + Skill |
| 真·多专业分工、可并行 | 多 Agent（B1）——先确认单 Agent 真的不够 |
| 生产、长流程、要可观测/重试 | Graph/Workflow（LangGraph）（C1） |

**决策口诀**：先问「单 Agent + 好工具 + 好上下文」能不能解决 → 不行再问缺什么 → 按缺的那一维度（推理/协作/编排）针对性加复杂度。

## 一句话总结

> 没有最好的架构，只有最合适的架构。**按维度选，不按「进化阶段」选；默认最简单，只在必要时加复杂度。**
