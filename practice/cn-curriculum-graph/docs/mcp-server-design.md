# MCP server 设计：把知识依赖图暴露给 agent

> 时间：2026-07-27。状态：设计已定，实现未开始。
> 前置：`docs/schema-design.md`（图长什么样）、`docs/pipeline-design.md`（图怎么来）。

## 0. 为什么现在做这件事

前面所有工作都在**造数据**：schema → 校验层 → judge → 生成流水线 → 编排对比 → 上量前的三件事。
造出来的东西有没有用，到今天为止**一次都没被验证过**。

具体说，这份 schema 相对 Marble 声称的四处增量里，`misconceptions` 是最大的一处
（"有了它，LLM 才能从『孩子答错了』推进到『孩子为什么这么想』"——`models.py` 的原话）。
这句话至今是**一个未经检验的断言**。`evidence`、`assessment_prompt` 同样。

MCP server 的目的不是"做一个 server"，是**把这些字段放到真实 agent 的取用路径上，看它们到底会不会被用起来**。
所以本文里每个工具都要回答一个问题：它压测的是哪个字段。压不到任何字段的工具不做。

## 1. 最有争议的一条决定：领域层不塞 LLM

诊断场景要把"孩子说 0.45 比 0.405 小"对应到知识点。直觉方案是在 server 里调一个模型做语义匹配。

**不做。** 理由：

MCP server 的消费方**本身就是一个 LLM**。它拿到检索返回的候选，自己会判断哪个对得上。
在 server 里再放一个模型，是把同一个推理做了两遍——正是 effective-agents 心法①
"不要什么都做成 Agent（先问 workflow 是否更对）"要拦的东西。

代价也是实打实的：server 需要 key、每次调用花钱、测试要注入 fake judge、启动依赖变重，
而这些成本换来的能力，消费端 agent 本来就有。

**所以领域层是纯检索 + 纯图算法：零 key、零成本、全可测。**

### 但"纯检索"不等于"检索得准"

中文分词与同义词是真问题。`"小数比大小"` 能命中，`"小数点后位数多就大"` 可能命中不了 ——
这时候只能靠 agent 换词重试，多耗轮次。

**这条不靠感觉，做成可测量的**：建一组诊断 ground truth（手写"孩子的错误说法 → 应该命中哪个
知识点"），量 `recall@k`。这与 `data/judge-eval-groundtruth.json` + `scripts/eval_judge.py`
是同一个路子——那套基建当初就是为了"有 ground truth 才敢信判定"，这里复用同一个原则：
**有 ground truth 才敢说检索够用**。

检索不准到什么程度算不可接受，由这组数字说了算，不由直觉说了算。

## 2. 分层：领域层纯函数 + 薄绑定

```
serve/query.py      纯函数：检索、图遍历、路径规划    ← 不 import 任何 mcp 符号
mcp_server.py       绑定：6 个 @tool，函数体只转发    ← 十几行
```

这正是手写 vs LangGraph 那轮用过的手法（六层纯函数一行不改，只换编排层，
见 `docs/langgraph-vs-handwritten.md`）。好处在这里更直接：

MCP Python SDK **v2 稳定版目标日期是 2026-07-28**（本文写于 07-27），
`FastMCP` 更名 `MCPServer`，协议从有状态双向改成无状态请求/响应。
v1.28.1 是今天的稳定版但官方已标注**维护模式**。

分层之后，v2 落地时只需再写一个绑定，领域层与全部测试一行不动 ——
顺带能量出"协议从有状态改无状态"对我们的设计到底有什么影响，又是一组受控对比。

先绑 v1.28.1（今天能跑通、客户端生态成熟）。

## 3. 工具面

六个工具，两条线。每个都标注它压测哪个字段 —— 这是本设计的验收锚点。

### 诊断线

| 工具 | 输入 | 输出 | 压测字段 |
|---|---|---|---|
| `match_misconceptions` | `observation`（孩子的错误说法）, `limit` | `[{topic_id, topic_name, statement, probe, correction_hint}]` | **`misconceptions.*`** |
| `search_topics` | `query`, `grade?`, `limit` | 精简卡片 `[{id, name, grade_start/end, description 摘要}]` | `name` / `description` |
| `get_topic` | `topic_id` | 完整节点 | `evidence` / `assessment_prompt` / `misconceptions` |

`match_misconceptions` 是这套工具里唯一一个**为 `misconceptions` 字段专门存在**的工具。
如果它在真实对话里从没被调用、或调用了也没帮上忙，那就是这个字段没有兑现承诺的直接证据 ——
这个结论即使是负面的也有价值，比继续假设它有用强。

### 规划线

| 工具 | 输入 | 输出 | 压测字段 |
|---|---|---|---|
| `get_prerequisites` | `topic_id`, `depth?`, `include_soft?` | 前置树，每条边带 `strength` 与 `reason` | `dependencies.strength/reason` |
| `plan_path` | `target_id`, `known_ids?` | 拓扑序学习序列，跳过已掌握，附相关 `revisits` | `dependencies` + `revisits` |

`include_soft` 单独开关：hard 是"必须先会"，soft 是"最好先会"。让 agent 自己决定要不要
把 soft 边算进路径，是把产品决策留在消费端而不是焊死在工具里。

**`known_ids` 的语义必须定死，否则两种读法差别很大**：传入的 id 视为**已掌握**，
它自己**和它的全部上游前置**一并从路径中剔除（"会了 X"蕴含"会了 X 的前置"）。
另一种读法是"只剔除 id 本身、上游照留"，那会在孩子已经会分数四则时还让他从整数加法学起。
选前者；后者若真有需要，是另一个参数，不是同一个参数的另一种解释。

### 元信息

| 工具 | 为什么需要 |
|---|---|
| `get_graph_stats` | 节点数、边数、年级分布、覆盖的课标编号 |

这个工具存在的理由很实际：**防止 agent 在一张 4 节点的图上假装自己在做课程规划**。
之前那次真实运行只产出 4 节点 1 边，任何"学习路径"在那张图上都是退化的。
让 agent 先知道自己在什么规模的图上工作，是诚实性的一部分。

### 每个返回体都带 provenance

所有返回知识点的工具，返回体里必须带 `provenance.review_status`（当前恒为 `unreviewed`）
与 `provenance.confidence`（恒为 `0.0`）。

理由见 `memory/learning-log.md` 2026-07-26 那条：**没有教研审核时任何非零置信度都是自欺**，
这是本项目从生成端就做成结构约束的一条原则。暴露层不能把它丢掉 ——
agent 必须知道它读的是未经审核的机器生成内容，否则前面所有的诚实性设计在最后一米前功尽弃。

## 4. 测试

**领域层**：全部 TDD，fixture 图手写，必须覆盖这些形状 ——
带环（防 `plan_path` 死循环）、soft 边、`revisits`、孤儿节点（无前置无后继）、
同名节点（生成的图里同名是高危区，见 memory 的三档判定那条）、空图。

**绑定层**：只测"接线" —— 六个工具都注册了、input schema 与领域层签名一致、
参数原样转发、返回体能被 pydantic 反解。不重复测领域层已经测过的行为。

**诊断评测**：`data/diagnosis-eval-groundtruth.json` + `scripts/eval_diagnosis.py`，
量 `recall@1/@3/@5`。低于阈值非零退出，与 `eval_judge.py` 同一套约定。

规模与阈值先定下来，免得跑完再"看着定"（那等于没有判据）：

- **ground truth ≥ 16 条**，与 judge 那套同量级。且必须包含边界样本 ——
  同义换词（"小数点后面位数多的大" vs 图里的"小数大小的比较"）、
  跨年级同主题（分数在三上/五下都出现）、以及**应当召回不到任何东西**的样本
  （问的是图里根本没有的知识点，检索必须敢返回空而不是硬凑一个）。
- **阈值 `recall@3 ≥ 0.75`**。定 @3 不定 @1：消费端是 LLM，给它三个候选自己挑是合理用法，
  强求 @1 是把工具当成分类器用，与"推理留给 agent"的设计前提矛盾。
- 这个阈值是**首版判据，不是目标**。跑完若明显偏低，结论可能是"纯检索不够用"，
  那就回到 §1 重新论证是否要引入 LLM —— 用数据推翻自己的设计决定，比守着它强。

## 5. 验收判据

**不是"测试全绿"**。是：

把 server 接进 Claude Code（`.mcp.json`），真实跑两段对话 ——

1. 诊断："我家孩子说 0.45 比 0.405 小，因为 45 比 405 小。他到底卡在哪？"
2. 规划："他要学会分数四则运算，按课标应该先补哪些？"

然后看**对话里 agent 实际调了哪些工具、`misconceptions`/`evidence` 有没有真的进入它的回答**。

这一步产出的应该是一段实录 + 一段诚实的评价，包括"某个字段其实没被用上"这种结论。

## 6. 已知不确定性

- **v2 时机**：目标日期不等于发布日期；即使明天发了，Claude Code 等客户端跟进新 spec 还需要时间。
  先绑 v1 是为了今天能验证，不是判断 v1 更好。
- **图的规模**：本次扩量后预计 30–50 节点。规划工具在这个规模上有意义，但离"覆盖小学数学"还远，
  只覆盖了"数与代数"一个领域。跨领域前置（如"分数"依赖"平均分"，后者属图形与几何/综合）会缺。
- **同名节点**：全量 Marble 数据上 86% 的名实不符 ERROR 落在跨年龄段复用的同名节点上。
  我们自己的图规模还小，这个问题未必暴露，但检索层要提前假设它会发生（返回候选带年级区分）。
- **中文检索质量**：见 §1，靠 ground truth 量，不靠猜。

## 7. 实测结果（2026-07-27，实现完成后补记）

设计写完当天实现完毕。三处与设计预期不同，如实记在这里。

### 7.1 §1 的赌注赢了，但赢得比预想的窄

"领域层不塞 LLM"这条决定顶住了第一次真实评测：22 条 ground truth 上
**recall@3 = 84%**（阈值 75%），"应当召回不到"的 3 条全部正确返回空。
零 key、零成本、64 节点图上单次查询在毫秒级。

但**首跑是 63%，闸门红**。逐条看未命中样本才发现，掉的不是"语义理解"，
是两个更蠢也更结构性的东西：

- **长度惩罚**：打分只算"查询被覆盖了多少"，而家长转述比图里的误概念长得多，
  分母里塞满"他说""一样"这类没有信息量的字，把真正对上的"交换/减法"
  稀释到门槛以下。**说得越具体越啰嗦，越被惩罚。**
- **表示层不同**：图里写 `1/4`、`5-3=3-5`，家长说"八分之一"、"5 减 3"，
  字面重叠是**零**。这不是同义词问题，是同一个数学对象的两种写法。

两处都不是"字面匹配的固有极限"，是实现缺陷。改完（两个方向的覆盖率取大者
+ 数学表达归一化）63% → 84%，**而 `MIN_RELEVANCE` 一个数没动**。

教训写在这里：**第一次评测跑出低分时，先看它是不是在量你以为它在量的东西。**
如果当时按设计文档 §4 那句"结论可能是纯检索不够用"直接去引入 LLM，
就会用一个模型去补一个除法写错了分母的窟窿。

### 7.2 一条失败的调优：IDF 加权

针对长度惩罚，第一反应是 IDF 加权（稀有字权重高）。**实测更差：63% → 53%。**

原因反直觉且值得记住：IDF 惩罚的是"**在图语料里**罕见"，而家长口语里的噪声词
（"他说""一样"）恰恰在图语料里从没出现过，df=0 → 权重取到最大，
把分母顶得更高。**方向正好搞反了。** 已回退，失败记录留在 `query.py` 的注释里。

### 7.3 §4 选 @3 不选 @1 的理由，在当前实现下不成立

设计里写：定 @3 是因为"消费端是 LLM，给它三个候选自己挑是合理用法"。
实测 **recall@1 == recall@3 == recall@5 == 84%，三个数完全相同**。

也就是说这个匹配器基本是二值的：要么第一名就命中，要么空手而归，
**排序维度是空的**。给三个候选和给一个候选没有区别。

推理本身没错（消费端确实是 LLM），但它描述的能力当前实现提供不了。
这不影响阈值取值，影响的是将来怎么改进：真要让 @3 比 @1 有意义，
得先有一个能把"差不多对"的候选排进第二三名的打分函数 —— 现在没有。

### 7.4 未验证的改进假设（标记为推断，不是实测）

剩下 3 条未命中里，`order_of_operations`（`20+5×2` vs 图里的 `15+3×4`）
指向同一件事：**具体数字换掉之后字面匹配就废了**。
一个可能的修法是把数字掩码成占位符再匹配（`<数>+<数>×<数>`）。

**这条没有实测过**，按本项目的待办纪律必须标清楚：它是"读到症状后想到的假设"，
不是"量出来的结论"。动手前先花十分钟证伪 —— 上一轮三条推断类待办全部前提不成立。

## 8. 验收：两段真实对话（2026-07-27，Claude Code + FastMCP 1.28.1）

按 §5 的判据跑完。**判据不是"能调通"，是 `misconceptions`/`evidence` 有没有真的
进入 agent 的回答** —— 下面逐字段核对，包括"某个字段其实没被用上"这种结论。

### 8.1 调用实录

**对话 1（诊断）**："我家孩子说 0.45 比 0.405 小，因为 45 比 405 小。他到底卡在哪？"

```
get_graph_stats()                        → 64 节点 / 31 边 / 26 孤立 / 最长链 3
match_misconceptions("我家孩子说 0.45 比 0.405 小，因为 45 比 405 小。")
                                         → 3 条：数感的进一步发展(0.375)
                                                 小数的意义(0.357)
                                                 分数的意义(0.273)
get_topic("t_95829346d7")  # 小数的意义
get_topic("t_a05c4749a1")  # 数感的进一步发展
```

**对话 2（规划）**："他要学会分数四则运算，按课标应该先补哪些？"

```
search_topics("分数四则运算")             → t_0b449c5333 (score 1.0) + 4 个相关
plan_path("t_0b449c5333")                → 只有 2 步：整数四则混合运算 → 目标
get_prerequisites("t_0b449c5333", 3)     → 1 条 hard 边
get_prerequisites("t_c45b4c385d", 3)     → 空（分数的意义是孤儿）
search_topics("通分 约分 公倍数")          → 节点存在，但没连到分数运算上
```

后两次调用是**换个说法回查**（工具 description 里就是这么写的），
用来确认"路径只有两步"是图真的这么稀，不是检索没命中。结论：是图的问题。

### 8.2 逐字段核对

| 字段 | 用上没有 | 证据 |
|---|---|---|
| `misconceptions.statement` | ✅ 诊断线的支点 | 「0.3 比 0.03 小」直接定位心智模型，且是**同型不同数** —— 纯字面检索给不了，只有这个字段能给 |
| `misconceptions.probe` | ✅ 原样用了 | 两条诱发提问一字未改进入回答 |
| `misconceptions.correction_hint` | ⚠️ 被改写了 | 图里给"关注数位：0.3 是 3 个 0.1"，agent 展开成钱币模型。**方向是它给的，话不是** |
| `evidence` | ✅ 用了 | 两条掌握判据成了"怎么算学会了" |
| `assessment_prompt` | ✅ 原样出口 | 「你能说说 0.3 表示什么意思吗」 |
| `standards` | ⚠️ 只报编号 | `3.1.2` 对家长几乎无意义 —— **这个字段的消费者是教研/教师，不是家长** |
| `dependencies.reason` | ✅ 用了 | "运算顺序直接迁移"原样成了"为什么先学这个" |
| `revisits` | ❌ 完全没用上 | 全图 `revisit_count = 0`，字段设计得再好也没数据 |
| `provenance` | ✅ 起了作用 | 两次回答都自动降级措辞、标注未审核 |

### 8.3 三条结论

**① `misconceptions` 兑现了承诺；`revisits` 没有机会兑现。**
前者是本 schema 相对 Marble 最大的赌注（`models.py` 原话："有了它，LLM 才能从
『孩子答错了』推进到『孩子为什么这么想』"）。诊断线上它确实做到了，
而且靠的是**同型不同数**的匹配 —— 那正是 §1 决定不放 LLM 时最担心的能力，
结果由字段本身补上了：误概念是**有限且可枚举**的，不需要语义模型也能对上。
后者是数据缺失（生成流水线一条 revisit 都没产出），不是设计失败，
但**至今仍是一个未经检验的字段** —— 与 MCP server 立项时 `misconceptions` 的处境相同。

**② 诊断线可用，规划线不可用 —— 而且是数据问题，不是工具问题。**
症状具体：分数四则的前置只有一条（整数混合运算），通分整条链没连出来，
`分数的意义` 是孤儿。agent 只能用自身知识补三步并明确标注来源。
**这恰恰说明 `get_graph_stats` 的设计意图起了作用**：先报 26/64 孤立、最长链 3 层，
agent 一开始就知道该打几折，没有在一张退化的图上假装做课程规划。

**③ 工具面缺一个方向：没有"谁以它为前置"。**
"他会了 X，接下来学什么"是家长的自然问题，六个工具答不了。
领域层有 `dependents_of`，只是没有工具暴露它 —— 设计时只想到了"往上找前置"，
没想到"往下找后继"。**这条是真跑对话才发现的，设计评审发现不了。**
但补工具排在修边质量之后：在同一张稀图上，新工具同样会大面积返回空。
