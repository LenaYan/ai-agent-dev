# 构建有效 Agent 的核心原则（贯穿全程的心法）

> 来源：Anthropic — Barry Zhang & Erik Schluntz，《Building Effective Agents》博客与同名分享。
> 定位：这不是「又一篇资料」，而是本工作区的**默认指导原则**。学任何主题、写任何 sample/practice 时都回来对照。
> 编写日期：2026-07-06 · ⚠️ 观点约 2024 年底提出，模型/生态在演进，但原则依然成立。

## 为什么把它抬到「原则」高度

- **一手权威源**：出自 Anthropic 官方，是「简单优先」共识的原始出处（`agent-architecture-patterns.md` 反复引用它）。
- **反炒作**：在人人吹「多 Agent / 全自主」时，官方却说「别都做成 Agent、尽量保持简单」。对资深工程师，这比框架教程更值钱。
- **可迁移**：它讲的是判断力与工程取舍，不随框架版本过时。

## 三条核心原则

### 1. 不要什么都做成 Agent（workflow vs agent）

Agent 是**扩展「复杂且高价值」任务的手段**，不是所有场景的即插即用升级。自主性要花钱买——**成本↑、延迟↑、错误后果↑**。

**「该不该做 Agent」检查清单**（本质是 ROI + 风险模型）：

| 维度 | 判断 |
|---|---|
| **任务复杂度** | 问题空间**模糊**才值得用 Agent；决策树清晰 → 直接写 workflow/代码并优化节点 |
| **任务价值** | 任务价值要配得上 Agent 成本；单次预算极低的高并发场景（如 10 美分/次的客服）→ 用 workflow 覆盖常见路径 |
| **任务可行性** | 行动路径无重大瓶颈；有瓶颈就**缩小范围、简化任务**再试 |
| **错误成本与可发现性** | 风险高且难发现 → 限权（只读）或加人工介入，但这会限制扩展能力 |

**「写代码」为何是好场景**（记住这条理由链）：
> 复杂模糊 + 高价值 + 模型擅长 + **输出可验证（单测/CI）**

> 💡 最后一条最关键：**有廉价验证回路的任务，才适合给高自主 Agent。** 没有验证回路，就降级为 workflow / 加人工确认。

### 2. 尽可能久地保持简单

Agent 的本质就一句：**模型在循环里使用工具（model using tools in a loop）**。最小骨架只有三件：

- **环境（Environment）**：Agent 运行的系统。
- **工具（Tools）**：Agent 行动并获取反馈的接口。
- **System Prompt**：定义目标、约束与理想行为。

**工程启示**：
- 迭代**先围绕这三件**打磨，行为稳定后再谈优化。
- 不同 Agent（编码/操作电脑/搜索）表面天差地别，**骨架相同**；你 90% 的设计功夫在「**给什么工具**」和「**怎么写 prompt / 工具描述**」，而不是搭复杂编排。
- ⚠️「简单」≠「容易」：复杂度被从「编排」挪到了「工具设计 + 上下文工程」，那里同样难，只是难在别处。

### 3. 像你的 Agent 一样思考（= 上下文工程思维）

模型眼里的世界 = **它上下文窗口里的内容**，仅此而已。把自己限制在同样的上下文里，才能看懂它的视角与盲区。

**两个可操作技巧**：
1. **亲自走一遍**：只用 Agent 能看到的信息完成一次任务，体会它的处境。
2. **用模型 debug 模型**：把 system prompt / 工具描述 / 完整轨迹丢给 Claude，问「指令有无歧义、工具会不会用、为何这么决策、怎么改进」。

## 仍未解决的前沿（别指望框架现在替你搞定）

Barry 提出的三个开放问题，至今仍是前沿方向：
- **预算意识**：如何定义/约束 Agent 的 token 与时间预算。
- **自我演化的工具**：模型改进自身工具可用性，形成「元工具」。
- **多 Agent 异步通信**：从同步 user/assistant 轮次扩展到异步协作与互相识别。

---

## 诚实的保留

- **有立场**：Anthropic 卖强单模型 + 工具，「保持简单、少用多 Agent」也部分契合其产品叙事。结论我认同（业界经验支持），但知道它非纯中立。
- **时效**：MCP、更长上下文、更强模型出现后，「简单骨架」的能力边界在外扩——但原则不变。

---

## 一句话记忆（若只记三件事）

1. **不要什么都做成 Agent**（先问：workflow 是不是更对？）。
2. **若要做，尽可能久地保持简单**（功夫下在工具 + prompt）。
3. **迭代时，像你的 Agent 一样思考**（练上下文工程）。
